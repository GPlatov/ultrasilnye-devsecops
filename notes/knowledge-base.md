# Knowledge Base — День 1 (Фундамент)

## 1) Репозиторий (Repository)
**Репозиторий** — это папка проекта + история изменений.
Git хранит историю в скрытой папке **.git**.

## 2) Коммит (Commit)
**Коммит** — это сохранённый “снимок” изменений.
В коммите есть: автор, время, сообщение и список изменений.

## 3) Ветка (Branch) и main
**Ветка** — отдельная линия изменений.
**main** — главная ветка проекта (то, что считается “основной версией”).

## 4) Git status (что я сегодня увидел)
Команда git status показала:
- On branch main
- nothing to commit, working tree clean
Это значит: я в ветке main и нет изменений, которые нужно сохранять.

## 5) CI (Continuous Integration) — простыми словами
**CI** — автоматические проверки проекта после того, как я отправил изменения на GitHub.
Цель CI: быстро поймать ошибки и проблемы безопасности.
Если CI зелёный ✅ — можно двигаться дальше.
Если CI красный ❌ — надо исправлять.

### 6) Security Gates (ворота безопасности)
Security Gates — это проверки в CI, которые НЕ пропускают опасные изменения в репозиторий.

В моём проекте сейчас стоят ворота:
1) Gitleaks — ищет секреты (токены/ключи). Нашёл → CI становится красным.
2) Trivy — ищет уязвимости уровня HIGH/CRITICAL. Нашёл → CI становится красным.

Идея: безопасность встроена в процесс, а не “потом”.

### 7) Remote / origin / push / pull (по-детски)
Remote — это удалённая копия репозитория (на GitHub).
origin — имя по умолчанию для remote.

git push — отправить мои коммиты на GitHub (в origin).
git pull — забрать свежие изменения с GitHub на мой компьютер.

## 8) SAST и CodeQL (простыми словами)

**SAST** — это поиск уязвимостей в коде без запуска программы.

**CodeQL** — это встроенный инструмент GitHub для SAST.
Он анализирует репозиторий и ищет потенциально опасные места в коде.

Где это видно:
- вкладка **Security**
- раздел **Code scanning**
- вкладка **Actions**, где запускается workflow **CodeQL**

Что я сделал:
- включил **CodeQL analysis**
- выбрал режим **Default setup**
- GitHub автоматически добавил и запустил проверку

Зачем мне это нужно:
- ловить проблемы в коде заранее
- усиливать безопасность проекта
- строить портфолио Security Engineer / DevSecOps.

## 9) Permissions в GitHub Actions (простыми словами)

**Permissions** — это права, которые получает workflow в GitHub Actions.

Если permissions не указать явно, workflow может получить права по умолчанию, которые шире, чем реально нужны.

Безопасный подход:
- давать только те права, которые действительно нужны
- не оставлять лишние разрешения “на всякий случай”

CodeQL нашёл у меня предупреждение:
"Workflow does not contain permissions"

Это значит:
в файле `.github/workflows/ci.yml` нужно явно указать блок permissions.

## 10) Case-study в портфолио (простыми словами)

Case-study — это оформленный разбор выполненной работы.

Он нужен, чтобы показать не только факт “я что-то делал”, но и:
- что именно я делал
- что было настроено или найдено
- какую проблему я увидел
- как я её исправил
- чему меня это научило

Для работодателя case-study важен потому, что он превращает GitHub из набора файлов в доказательство практики.

Связка выглядит так:
- README = входная витрина
- case-study = подтверждение, что я реально работал руками
- knowledge-base = подтверждение, что я понимаю смысл того, что делаю.
## 14) Ubuntu VM: постоянный IP, SSH и базовая сеть

### Цель этапа

Сделать Ubuntu Server стабильной учебной виртуальной машиной для DevOps-лаборатории.

Главная рабочая цепочка:

```text
Windows PowerShell → SSH → Ubuntu Server
```

Эта цепочка нужна для того, чтобы управлять Linux-сервером удалённо, как это обычно делается в инфраструктуре и DevOps.

---

### 1. Как понять, где я нахожусь

Если я вижу:

```powershell
PS C:\Users\Герман>
```

значит я нахожусь в Windows PowerShell.  
Команды выполняются в Windows.

Если я вижу:

```bash
germanix@ubuntuserver1:~$
```

значит я нахожусь внутри Ubuntu Server, обычно через SSH.  
Команды выполняются в Linux.

Важно:

```text
Окно может быть PowerShell, но после команды ssh я уже управляю Ubuntu.
```

---

### 2. Что такое SSH

SSH расшифровывается как Secure Shell.

SSH — это защищённый способ удалённого подключения к Linux-серверу через терминал.

В моей лаборатории SSH нужен, чтобы подключаться из Windows к Ubuntu Server:

```powershell
ssh germanix@192.168.56.101
```

Где:

```text
germanix = пользователь Ubuntu
192.168.56.101 = IP-адрес Ubuntu для SSH
```

SSH — основной рабочий способ администрирования Linux-сервера.

---

### 3. IP Ubuntu для SSH

Для Ubuntu закреплён IP:

```text
192.168.56.101
```

Команда подключения из Windows:

```powershell
ssh germanix@192.168.56.101
```

Почему нужен постоянный IP:

```text
Сервер должен быть доступен всегда по одному и тому же адресу.
```

Если IP будет меняться, могут ломаться:

- SSH-подключение
- GitLab
- GitLab Runner
- Nginx
- custom domain
- pipeline
- будущая DevOps-лаборатория

Главная идея:

```text
Постоянный IP = предсказуемый доступ к серверу.
```

---

### 4. Сетевые интерфейсы Ubuntu

В моей Ubuntu VM используются два основных интерфейса:

```text
enp0s3
enp0s8
```

#### enp0s3

`enp0s3` — NAT-интерфейс.

Назначение:

- выход Ubuntu в интернет
- установка пакетов
- обновления
- будущая установка Docker
- будущая установка GitLab Runner
- доступ к внешним репозиториям

Пример IP:

```text
10.0.2.15/24
```

Коротко:

```text
enp0s3 = NAT = интернет для Ubuntu
```

#### enp0s8

`enp0s8` — Host-Only-интерфейс.

Назначение:

- связь между Windows-хостом и Ubuntu VM
- SSH-доступ из Windows в Ubuntu
- стабильный адрес для администрирования виртуальной машины

IP:

```text
192.168.56.101/24
```

Коротко:

```text
enp0s8 = Host-Only = связь Windows ↔ Ubuntu
```

---

### 5. Проверка сети из Windows

Проверить, видит ли Windows Ubuntu по сети:

```powershell
ping 192.168.56.101 -n 4
```

Если ответы есть, значит Windows видит Ubuntu по сети.

Проверить SSH-подключение:

```powershell
ssh germanix@192.168.56.101
```

Если подключение успешно, появляется строка вида:

```bash
germanix@ubuntuserver1:~$
```

---

### 6. Проверка сети внутри Ubuntu

Кратко показать IP-адреса:

```bash
ip -br addr
```

Ожидаемая картина:

```text
enp0s3 UP 10.0.2.15/24
enp0s8 UP 192.168.56.101/24
```

Проверить интернет по IP:

```bash
ping -c 4 8.8.8.8
```

Проверить DNS:

```bash
ping -c 4 google.com
```

---

### 7. Windows ping и Linux ping

В Windows используется:

```powershell
ping 192.168.56.101 -n 4
```

В Linux используется:

```bash
ping -c 4 192.168.56.101
```

Смысл одинаковый:

```text
проверить доступность узла по сети
```

Но флаги разные:

```text
Windows: -n 4
Linux:   -c 4
```

Ошибка, которую важно не повторять:

```bash
ping 192.168.56.101 -n 4
```

Это Windows-стиль команды, и в Linux он работает неправильно.

---

### 8. DNS

DNS — это система, которая преобразует доменное имя в IP-адрес.

Пример:

```text
google.com → IP-адрес сервера Google
```

Если работает:

```bash
ping -c 4 8.8.8.8
```

но не работает:

```bash
ping -c 4 google.com
```

значит:

```text
интернет по IP есть, но DNS не работает
```

То есть Ubuntu не может преобразовать доменное имя `google.com` в IP-адрес.

---

### 9. Netplan

Netplan — это механизм настройки сети в Ubuntu.

Файл сетевой конфигурации:

```bash
/etc/netplan/50-lab-network.yaml
```

Этот файл нужен, чтобы описать, как Ubuntu должна настраивать сетевые интерфейсы.

В моей лаборатории netplan делает следующее:

- `enp0s3` получает интернет через DHCP/NAT
- `enp0s8` получает постоянный IP `192.168.56.101/24`

Ожидаемое содержимое файла:

```yaml
network:
  version: 2
  ethernets:
    enp0s3:
      dhcp4: true
      optional: true
    enp0s8:
      addresses:
        - 192.168.56.101/24
      optional: true
```

Проверить содержимое файла:

```bash
sudo cat /etc/netplan/50-lab-network.yaml
```

Проверить синтаксис netplan:

```bash
sudo netplan generate
```

Если команда ничего не выводит — это хороший знак.  
Значит синтаксис корректный.

Применить настройки:

```bash
sudo netplan apply
```

Безопасное применение с возможностью отката:

```bash
sudo netplan try
```

---

### 10. Права на netplan-файл

После создания netplan-файла может появиться предупреждение:

```text
Permissions for /etc/netplan/50-lab-network.yaml are too open.
```

Это значит, что файл сетевой конфигурации доступен слишком широко.

Исправление:

```bash
sudo chmod 600 /etc/netplan/50-lab-network.yaml
```

Смысл `chmod 600`:

```text
читать и изменять файл может только владелец/root
остальные пользователи не имеют доступа
```

Почему это важно:

```text
сетевые конфиги не должны быть доступны всем пользователям
```

---

### 11. Если SSH не работает

Если при подключении:

```powershell
ssh germanix@192.168.56.101
```

появляется ошибка:

```text
Connection timed out
```

это обычно проблема сети, а не пароля.

Если пароль неправильный, чаще будет ошибка типа:

```text
Permission denied
```

`Connection timed out` означает:

```text
Windows не может достучаться до Ubuntu по сети
```

Порядок диагностики:

1. Проверить, включена ли Ubuntu VM.
2. Проверить, есть ли IP `192.168.56.101/24` на `enp0s8`.
3. Проверить ping из Windows:

```powershell
ping 192.168.56.101 -n 4
```

4. Проверить SSH-сервис внутри Ubuntu:

```bash
systemctl status ssh --no-pager
```

5. Если SSH не запущен, запустить:

```bash
sudo systemctl start ssh
```

6. Проверить, слушает ли порт 22:

```bash
sudo ss -tulpn | grep :22
```

7. Проверить firewall:

```bash
sudo ufw status
```

8. Если SSH недоступен, зайти через VirtualBox-консоль и восстановить сеть вручную.

---

### 12. Временное восстановление IP

Если SSH не работает, а у `enp0s8` нет IP `192.168.56.101/24`, нужно зайти через VirtualBox-консоль и временно назначить IP:

```bash
sudo ip link set enp0s8 up
sudo ip addr add 192.168.56.101/24 dev enp0s8
ip -br addr show enp0s8
```

Если появляется сообщение:

```text
Address already assigned
```

это не ошибка.

Это значит:

```text
IP уже назначен
```

---

### 13. VirtualBox-консоль и SSH

VirtualBox-консоль — аварийный доступ.

Она нужна, если:

- сломалась сеть
- пропал IP
- SSH не работает
- netplan настроен неправильно
- нужно восстановить доступ вручную

SSH — основной рабочий доступ.

Он нужен для нормального удалённого администрирования Linux-сервера по сети.

Коротко:

```text
VirtualBox-консоль = аварийный доступ
SSH = основной рабочий доступ
```

## 12) Linux 2.1: ориентация на сервере

### Цель блока

Научиться после подключения к Linux-серверу быстро понимать:

- под каким пользователем я работаю
- на каком сервере нахожусь
- в какой папке нахожусь
- где моя домашняя папка
- какие файлы и папки находятся рядом

Главная логика процесса:

```text
подключился к серверу → понял кто я → понял где я → посмотрел окружение
```

Это базовый процесс перед любой работой в Linux.

Если я не понимаю, где нахожусь и под каким пользователем работаю, я могу выполнить команду не там, изменить не тот файл или сломать конфигурацию.

---

### Основная рабочая строка Linux

Если я вижу:

```bash
germanix@ubuntuserver1:~$
```

это означает:

```text
germanix = текущий пользователь
ubuntuserver1 = имя сервера
~ = домашняя папка текущего пользователя
$ = обычный пользователь, не root
```

Если вместо `$` был бы символ `#`, это означало бы, что я работаю под root.

---

### Команды ориентации

#### 1. Текущий пользователь

```bash
whoami
```

Показывает, под каким пользователем я сейчас работаю.

Пример результата:

```text
germanix
```

Смысл:

```text
Я работаю как обычный пользователь germanix, а не как root.
```

---

#### 2. Имя сервера

```bash
hostname
```

Показывает имя сервера.

Пример результата:

```text
ubuntuserver1
```

Смысл:

```text
Я понимаю, на какой машине сейчас нахожусь.
```

Это важно, потому что в реальной инфраструктуре может быть много серверов: GitLab-сервер, runner-сервер, сервер мониторинга, тестовая VM и так далее.

---

#### 3. Текущая папка

```bash
pwd
```

`pwd` расшифровывается как:

```text
print working directory
```

Команда показывает полный путь до текущей рабочей папки.

Пример результата:

```text
/home/germanix
```

Смысл:

```text
Я понимаю, где сейчас нахожусь в файловой системе Linux.
```

---

#### 4. Домашняя папка пользователя

```bash
echo $HOME
```

Показывает домашнюю папку текущего пользователя.

Пример результата:

```text
/home/germanix
```

`$HOME` — это переменная окружения, в которой хранится путь к домашней папке пользователя.

---

#### 5. Обычный список файлов

```bash
ls
```

Показывает обычное содержимое текущей папки.

Пример результата:

```text
linux-lab
```

Смысл:

```text
Я вижу обычные файлы и папки, которые находятся в текущей директории.
```

---

#### 6. Подробный список файлов

```bash
ls -la
```

Показывает подробное содержимое текущей папки, включая скрытые файлы.

Флаги:

```text
-l = long format, подробный вывод
-a = all, показать все файлы, включая скрытые
```

`ls -la` показывает:

- права доступа
- количество ссылок
- владельца
- группу
- размер
- дату изменения
- имя файла или папки
- скрытые файлы

---

### Домашняя папка

Домашняя папка пользователя `germanix`:

```text
/home/germanix
```

Символ:

```text
~
```

означает домашнюю папку текущего пользователя.

Для пользователя `germanix`:

```text
~ = /home/germanix
```

Поэтому строка:

```bash
germanix@ubuntuserver1:~$
```

означает, что я нахожусь в домашней папке пользователя `germanix`.

---

### Скрытые файлы

Файлы и папки, которые начинаются с точки, считаются скрытыми.

Примеры:

```text
.bash_history
.bashrc
.profile
.ssh
.config
.cache
```

Обычная команда:

```bash
ls
```

может их не показывать.

Команда:

```bash
ls -la
```

показывает скрытые файлы и папки.

---

### Что означают `.` и `..`

В выводе `ls -la` есть специальные обозначения:

```text
.  = текущая папка
.. = папка уровнем выше
```

Если текущая папка:

```text
/home/germanix
```

то:

```text
.  = /home/germanix
.. = /home
```

Это важно для понимания перемещения по файловой системе.

---

### Частые ошибки

#### Ошибка 1: опечатка в команде

Неправильно:

```bash
woami
```

Правильно:

```bash
whoami
```

Linux очень буквальный: если команда введена с ошибкой, она не выполнится.

---

#### Ошибка 2: попытка очистить экран командой `c`

Неправильно:

```bash
c
```

Правильно:

```bash
clear
```

Команда `clear` очищает экран терминала.

---

#### Ошибка 3: попытка выйти из SSH командой `disconnect`

Неправильно:

```bash
disconnect
```

Правильно:

```bash
exit
```

или:

```text
Ctrl + D
```

Команда `exit` завершает текущую SSH-сессию и возвращает меня обратно в Windows PowerShell.

---

### Как правильно выйти из SSH

Если я нахожусь внутри Ubuntu через SSH и хочу выйти обратно в Windows PowerShell, использую:

```bash
exit
```

или:

```text
Ctrl + D
```

После выхода я снова увижу строку Windows PowerShell вида:

```powershell
PS C:\Users\Герман>
```

---

### Критерий понимания блока

Я должен уметь без подсказки объяснить:

1. Что показывает `whoami`

3. Что показывает `pwd`
4. Что означает символ `~`
5. Что показывает `echo $HOME`
6. Чем отличается `ls` от `ls -la`

8. Как правильно выйти из SSH-сессии
9. Почему перед работой на сервере нужно понимать текущий контекст


Команда читается так:

```text
скопируй note.txt в note-copy.txt
```

Это означает:

```text
renamed-note.txt
```

Формат команды:

Расшифровка:


Было:

```text

```

Стало:

```text
files-practice/archive/renamed-note.txt
```

### Удаление файлов


Ошибка, которую важно не повторять:

```text

```

### Удаление папок с содержимым


`-r` означает `recursive`.

Смысл:

```text
удалить папку вместе со всем содержимым внутри
```

---

### Почему `rm` опасен

В Linux команда `rm` обычно удаляет без корзины.

В Windows файл часто можно восстановить из корзины.

В Linux после `rm` файл может исчезнуть сразу.

Поэтому перед `rm` всегда нужно проверять:

```bash
pwd
ls -la
```

---

### Правило перед `rm`, `cp`, `mv`

Перед командами:

```bash
rm
cp
mv
```

нужно выполнить:

```bash
pwd
ls -la
```

Зачем:

```text
pwd показывает, где я нахожусь.
ls -la показывает, какие файлы и папки реально есть.
```

Это нужно, чтобы не удалить, не скопировать и не переместить не тот файл.

Главное правило:

```text
Сначала понять контекст, потом выполнять действие.
```


Из-за этого команда может не выполниться.

Решение:

```text
стереть строку и вставить команду заново аккуратно
```

Важно:

```text
cat app.log — показать файл
```

### Просмотр файла через cat

```text
head нужен, чтобы быстро посмотреть начало файла.
```

```bash
tail app.log
```

Показать последние 3 строки:

Смысл:

```text
tail нужен, чтобы быстро посмотреть последние события в файле.
```

### Поиск строк через grep

`grep` ищет строки внутри файла.

Найти предупреждения:

```bash
grep WARN app.log
```

Найти информационные строки:

```bash
grep INFO app.log
```


Найти строки со словом `Database`:

### Полезные флаги grep



### Поиск файлов и папок через find

`find` ищет файлы и папки в файловой системе.

Главное отличие:

```text
grep ищет строки внутри файла.
find ищет файлы и папки.
```

Найти файл `app.log` от текущей папки:

```bash
find . -name "app.log"
```

Найти все `.log` файлы:

```bash
find . -name "*.log"
```

Найти все `.txt` файлы:

```bash
find . -name "*.txt"
```

Найти всё, где в имени есть `note`:

```bash
find . -name "*note*"
```

Показать только файлы:

```bash
find . -type f
```

Показать только папки:

```bash
find . -type d
```

Искать `app.log`, начиная с папки `~/linux-lab`:

```bash
find ~/linux-lab -name "app.log"
```

```text
-type f = искать только файлы
-type d = искать только папки
*       = любые символы
```

Пример:

```bash
find . -name "*.log"
```

означает:

```text
найти в текущей папке и ниже все файлы/папки, имя которых заканчивается на .log
```


### Что показывает ls -la

Пример строки:

Разбор:

```text
-rw-r--r--   1   germanix   germanix   213   May 19 23:46   app.log
│            │   │          │          │     │              │

│            │   │          │          │     └──────────────── дата изменения
│            │   │          │          └────────────────────── размер в байтах
│            │   │          └───────────────────────────────── группа
│            │   └──────────────────────────────────────────── владелец
│            └──────────────────────────────────────────────── количество жёстких ссылок
└───────────────────────────────────────────────────────────── тип объекта и права
```

Первый символ показывает тип объекта:

```text
- = обычный файл
d = директория / папка
```

Примеры:

```text
-rw-r--r-- = обычный файл
drwxr-xr-x = директория
```

Число после прав:

```text
-rw-r--r-- 1 germanix germanix app.log
```

`1` — это количество жёстких ссылок. Для обычного файла чаще всего будет `1`. Для папок может быть `2` и больше.

На текущем этапе важно запомнить:

```text
число после прав — это не права, не владелец и не размер.
Это отдельное поле ls -la.
```

### Owner, group, others

Linux делит доступ к файлу или папке на три группы:

```text
owner  = владелец
group  = группа
others = остальные пользователи
```

Пример:

```text
-rw-r--r--
```

Разбор:

```text
-   rw-   r--   r--
│    │     │     │
│    │     │     └── others / остальные
│    │     └──────── group / группа
│    └────────────── owner / владелец
└─────────────────── тип объекта
```

Для файла `app.log`:

```text
-rw-r--r-- 1 germanix germanix app.log
```

означает:

```text
тип объекта: обычный файл
владелец: germanix
группа: germanix
права владельца: rw-
права группы: r--
права остальных: r--
```

---

### Что означают r, w, x

Базовые права:

```text
r = read    = читать
w = write   = писать / изменять
x = execute = выполнять
```

Для файла:

```text
r = можно прочитать файл
w = можно изменить файл
x = можно выполнить файл как программу или скрипт
```

Для папки:

```text
r = можно увидеть список файлов внутри
w = можно создавать, удалять и переименовывать внутри
x = можно зайти в папку через cd
```

Критически важное отличие:

```text
x для файла = выполнить файл
x для папки = зайти внутрь папки
```

Пример:

```bash
cd archive
```

Чтобы зайти в папку, на неё нужно право `x`.

---

### Числовые права chmod

`chmod` меняет права доступа к файлу или папке.

```text
chmod = change mode
```

Каждому праву соответствует число:

```text
r = 4
w = 2
x = 1
```

Одна цифра получается сложением нужных прав:

```text
0 = --- = нет прав
1 = --x = только выполнение
2 = -w- = только запись
3 = -wx = запись + выполнение
4 = r-- = только чтение
5 = r-x = чтение + выполнение
6 = rw- = чтение + запись
7 = rwx = чтение + запись + выполнение
```

Главная таблица:

```text
7 = rwx = 4 + 2 + 1
6 = rw- = 4 + 2
5 = r-x = 4 + 1
4 = r-- = 4
0 = --- = нет прав
```

---

### Почему chmod использует три цифры

Формат:

```bash
chmod XYZ file
```

Где:

```text
X = права владельца
Y = права группы
Z = права остальных
```

Пример:

```bash
chmod 644 app.log
```

Расшифровка:

```text
6 = владелец: rw-
4 = группа: r--
4 = остальные: r--
```

Итог:

```text
644 = rw-r--r--
```

То есть:

```text
владелец может читать и изменять файл
группа может только читать
остальные могут только читать
```

---

### Главные режимы

#### chmod 600

```text
600 = rw-------
```

Разбор:

```text
6 = владелец: читать + писать
0 = группа: нет прав
0 = остальные: нет прав
```

Смысл:

```text
только владелец может читать и изменять файл
никто другой не имеет доступа
```

Применение:

```text
SSH-ключи
секреты
файлы с паролями
чувствительные конфиги
```

Пример:

```bash
chmod 600 private.key
```

---

#### chmod 644

```text
644 = rw-r--r--
```

Разбор:

```text
6 = владелец: читать + писать
4 = группа: читать
4 = остальные: читать
```

Смысл:

```text
владелец может читать и изменять
группа и остальные могут только читать
```

Применение:

```text
обычные файлы
логи
конфиги
документация
```

Пример:

```bash
chmod 644 app.log
```

---

#### chmod 755

```text
755 = rwxr-xr-x
```

Разбор:

```text
7 = владелец: читать + писать + выполнять
5 = группа: читать + выполнять
5 = остальные: читать + выполнять
```

Смысл:

```text
владелец может всё
группа и остальные могут читать и выполнять
но не могут изменять
```

Применение:

```text
скрипты
исполняемые файлы
папки
```

Пример:

```bash
chmod 755 deploy.sh
```

После этого скрипт можно попытаться запустить:

```bash
./deploy.sh
```

Важно:

```text
право x не превращает любой текстовый файл в рабочую программу.
Оно только разрешает системе попытку выполнить файл.
```

### Практика chmod

Рабочая папка:

```bash
cd ~/linux-lab/files-practice
```

Создание тестового файла:

```bash
touch permissions-demo.txt
echo "permissions test" > permissions-demo.txt
```

Проверка стартовых прав:

```bash
ls -la permissions-demo.txt
```

У меня стартовые права были:

```text
-rw-rw-r-- permissions-demo.txt
```

Это:

```text
664 = rw-rw-r--
```

То есть:

```text
владелец: читать + писать
группа: читать + писать
остальные: читать
```

Стартовые права могут отличаться в зависимости от настроек системы. Главное — `chmod` принудительно выставляет нужный режим.

Команды практики:

```bash
chmod 600 permissions-demo.txt
ls -la permissions-demo.txt

chmod 644 permissions-demo.txt
ls -la permissions-demo.txt

chmod 755 permissions-demo.txt
ls -la permissions-demo.txt
```

Результат:

```text
chmod 600 -> -rw-------
chmod 644 -> -rw-r--r--
chmod 755 -> -rwxr-xr-x
```

### chown

`chown` меняет владельца и/или группу файла.

```text
chown = change owner
```

Главная разница:

```text
chmod = меняет права
chown = меняет владельца и группу
```

Пример строки:

```text
-rw-r--r-- 1 germanix germanix app.log
```

Здесь:

```text
права: rw-r--r--
владелец: germanix
группа: germanix
```

Команда:

```bash
sudo chown root:root app.log
```

означает:

```text
владелец станет root
группа станет root
```

То есть:

```text
root:root
│    │
│    └── группа
└─────── владелец
```

Команда:

```bash
sudo chown germanix:germanix app.log
```

возвращает:

```text
владелец = germanix
группа = germanix
```

---

### sudo

`sudo` позволяет выполнить команду с повышенными правами, обычно от имени `root`.

Примеры:

```bash
sudo chown root:root file
sudo chmod 600 file
sudo apt update
sudo systemctl restart ssh
```

Важно:

```text
sudo не нужно использовать бездумно.
sudo даёт больше прав, значит ошибочная команда может нанести больше вреда.
```

Правильная логика:

```text
обычные действия выполняю как germanix
административные действия выполняю через sudo
перед sudo понимаю, что команда делает
```

### Практика chown и Permission denied

Файл сначала принадлежал пользователю `germanix`:

```text
-rwxr-xr-x 1 germanix germanix permissions-demo.txt
```

Команда:

```bash
sudo chown root:root permissions-demo.txt
```

изменила владельца и группу:

```text
-rwxr-xr-x 1 root root permissions-demo.txt
```

После этого команда:

```bash
echo "second line" >> permissions-demo.txt
```

дала ошибку:

```text
Permission denied
```

Почему:

```text
файл принадлежит root
текущий пользователь germanix больше не владелец
при правах 755 писать может только владелец
для группы и остальных есть только r-x
права w для germanix нет
```

Возврат владельца:

```bash
sudo chown germanix:germanix permissions-demo.txt
chmod 644 permissions-demo.txt
```

После этого запись снова прошла:

```bash
echo "second line" >> permissions-demo.txt
cat permissions-demo.txt
```

Результат:

```text
permissions test
second line
```

### Главный вывод

Права и владельцы — это базовый механизм безопасности Linux.

Коротко:

```text
ls -la = посмотреть права, владельца и группу
chmod = изменить права
chown = изменить владельца/группу
sudo = выполнить команду с повышенными правами
```

Главная практическая мысль:

```text
при ошибке Permission denied сначала смотрю права и владельца,
а не сразу бездумно пишу sudo.
```
