# Knowledge Base — День 1 (Фундамент)

## 1) Репозиторий (Repository)
**Репозиторий** — это папка проекта + история изменений.
Git хранит историю в скрытой папке **.git**.

## 2) Коммит (Commit)
**Коммит** — это сохранённый “снимок” изменений.
В коммите есть: автор, время, сообщение и список изменений.

## 3) Ветка (Branch) и main
**Ветка** — отдельная линия изменений.
**main** — главная ветка проекта (то, что считается “основной версией”).

## 4) Git status (что я сегодня увидел)
Команда git status показала:
- On branch main
- nothing to commit, working tree clean
Это значит: я в ветке main и нет изменений, которые нужно сохранять.

## 5) CI (Continuous Integration) — простыми словами
**CI** — автоматические проверки проекта после того, как я отправил изменения на GitHub.
Цель CI: быстро поймать ошибки и проблемы безопасности.
Если CI зелёный ✅ — можно двигаться дальше.
Если CI красный ❌ — надо исправлять.

### 6) Security Gates (ворота безопасности)
Security Gates — это проверки в CI, которые НЕ пропускают опасные изменения в репозиторий.

В моём проекте сейчас стоят ворота:
1) Gitleaks — ищет секреты (токены/ключи). Нашёл → CI становится красным.
2) Trivy — ищет уязвимости уровня HIGH/CRITICAL. Нашёл → CI становится красным.

Идея: безопасность встроена в процесс, а не “потом”.

### 7) Remote / origin / push / pull (по-детски)
Remote — это удалённая копия репозитория (на GitHub).
origin — имя по умолчанию для remote.

git push — отправить мои коммиты на GitHub (в origin).
git pull — забрать свежие изменения с GitHub на мой компьютер.

## 8) SAST и CodeQL (простыми словами)

**SAST** — это поиск уязвимостей в коде без запуска программы.

**CodeQL** — это встроенный инструмент GitHub для SAST.
Он анализирует репозиторий и ищет потенциально опасные места в коде.

Где это видно:
- вкладка **Security**
- раздел **Code scanning**
- вкладка **Actions**, где запускается workflow **CodeQL**

Что я сделал:
- включил **CodeQL analysis**
- выбрал режим **Default setup**
- GitHub автоматически добавил и запустил проверку

Зачем мне это нужно:
- ловить проблемы в коде заранее
- усиливать безопасность проекта
- строить портфолио Security Engineer / DevSecOps.

## 9) Permissions в GitHub Actions (простыми словами)

**Permissions** — это права, которые получает workflow в GitHub Actions.

Если permissions не указать явно, workflow может получить права по умолчанию, которые шире, чем реально нужны.

Безопасный подход:
- давать только те права, которые действительно нужны
- не оставлять лишние разрешения “на всякий случай”

CodeQL нашёл у меня предупреждение:
"Workflow does not contain permissions"

Это значит:
в файле `.github/workflows/ci.yml` нужно явно указать блок permissions.

## 10) Case-study в портфолио (простыми словами)

Case-study — это оформленный разбор выполненной работы.

Он нужен, чтобы показать не только факт “я что-то делал”, но и:
- что именно я делал
- что было настроено или найдено
- какую проблему я увидел
- как я её исправил
- чему меня это научило

Для работодателя case-study важен потому, что он превращает GitHub из набора файлов в доказательство практики.

Связка выглядит так:
- README = входная витрина
- case-study = подтверждение, что я реально работал руками
- knowledge-base = подтверждение, что я понимаю смысл того, что делаю.
## 14) Ubuntu VM: постоянный IP, SSH и базовая сеть

### Цель этапа

Сделать Ubuntu Server стабильной учебной виртуальной машиной для DevOps-лаборатории.

Главная рабочая цепочка:

```text
Windows PowerShell → SSH → Ubuntu Server
```

Эта цепочка нужна для того, чтобы управлять Linux-сервером удалённо, как это обычно делается в инфраструктуре и DevOps.

---

### 1. Как понять, где я нахожусь

Если я вижу:

```powershell
PS C:\Users\Герман>
```

значит я нахожусь в Windows PowerShell.  
Команды выполняются в Windows.

Если я вижу:

```bash
germanix@ubuntuserver1:~$
```

значит я нахожусь внутри Ubuntu Server, обычно через SSH.  
Команды выполняются в Linux.

Важно:

```text
Окно может быть PowerShell, но после команды ssh я уже управляю Ubuntu.
```

---

### 2. Что такое SSH

SSH расшифровывается как Secure Shell.

SSH — это защищённый способ удалённого подключения к Linux-серверу через терминал.

В моей лаборатории SSH нужен, чтобы подключаться из Windows к Ubuntu Server:

```powershell
ssh germanix@192.168.56.101
```

Где:

```text
germanix = пользователь Ubuntu
192.168.56.101 = IP-адрес Ubuntu для SSH
```

SSH — основной рабочий способ администрирования Linux-сервера.

---

### 3. IP Ubuntu для SSH

Для Ubuntu закреплён IP:

```text
192.168.56.101
```

Команда подключения из Windows:

```powershell
ssh germanix@192.168.56.101
```

Почему нужен постоянный IP:

```text
Сервер должен быть доступен всегда по одному и тому же адресу.
```

Если IP будет меняться, могут ломаться:

- SSH-подключение
- GitLab
- GitLab Runner
- Nginx
- custom domain
- pipeline
- будущая DevOps-лаборатория

Главная идея:

```text
Постоянный IP = предсказуемый доступ к серверу.
```

---

### 4. Сетевые интерфейсы Ubuntu

В моей Ubuntu VM используются два основных интерфейса:

```text
enp0s3
enp0s8
```

#### enp0s3

`enp0s3` — NAT-интерфейс.

Назначение:

- выход Ubuntu в интернет
- установка пакетов
- обновления
- будущая установка Docker
- будущая установка GitLab Runner
- доступ к внешним репозиториям

Пример IP:

```text
10.0.2.15/24
```

Коротко:

```text
enp0s3 = NAT = интернет для Ubuntu
```

#### enp0s8

`enp0s8` — Host-Only-интерфейс.

Назначение:

- связь между Windows-хостом и Ubuntu VM
- SSH-доступ из Windows в Ubuntu
- стабильный адрес для администрирования виртуальной машины

IP:

```text
192.168.56.101/24
```

Коротко:

```text
enp0s8 = Host-Only = связь Windows ↔ Ubuntu
```

---

### 5. Проверка сети из Windows

Проверить, видит ли Windows Ubuntu по сети:

```powershell
ping 192.168.56.101 -n 4
```

Если ответы есть, значит Windows видит Ubuntu по сети.

Проверить SSH-подключение:

```powershell
ssh germanix@192.168.56.101
```

Если подключение успешно, появляется строка вида:

```bash
germanix@ubuntuserver1:~$
```

---

### 6. Проверка сети внутри Ubuntu

Кратко показать IP-адреса:

```bash
ip -br addr
```

Ожидаемая картина:

```text
enp0s3 UP 10.0.2.15/24
enp0s8 UP 192.168.56.101/24
```

Проверить интернет по IP:

```bash
ping -c 4 8.8.8.8
```

Проверить DNS:

```bash
ping -c 4 google.com
```

---

### 7. Windows ping и Linux ping

В Windows используется:

```powershell
ping 192.168.56.101 -n 4
```

В Linux используется:

```bash
ping -c 4 192.168.56.101
```

Смысл одинаковый:

```text
проверить доступность узла по сети
```

Но флаги разные:

```text
Windows: -n 4
Linux:   -c 4
```

Ошибка, которую важно не повторять:

```bash
ping 192.168.56.101 -n 4
```

Это Windows-стиль команды, и в Linux он работает неправильно.

---

### 8. DNS

DNS — это система, которая преобразует доменное имя в IP-адрес.

Пример:

```text
google.com → IP-адрес сервера Google
```

Если работает:

```bash
ping -c 4 8.8.8.8
```

но не работает:

```bash
ping -c 4 google.com
```

значит:

```text
интернет по IP есть, но DNS не работает
```

То есть Ubuntu не может преобразовать доменное имя `google.com` в IP-адрес.

---

### 9. Netplan

Netplan — это механизм настройки сети в Ubuntu.

Файл сетевой конфигурации:

```bash
/etc/netplan/50-lab-network.yaml
```

Этот файл нужен, чтобы описать, как Ubuntu должна настраивать сетевые интерфейсы.

В моей лаборатории netplan делает следующее:

- `enp0s3` получает интернет через DHCP/NAT
- `enp0s8` получает постоянный IP `192.168.56.101/24`

Ожидаемое содержимое файла:

```yaml
network:
  version: 2
  ethernets:
    enp0s3:
      dhcp4: true
      optional: true
    enp0s8:
      addresses:
        - 192.168.56.101/24
      optional: true
```

Проверить содержимое файла:

```bash
sudo cat /etc/netplan/50-lab-network.yaml
```

Проверить синтаксис netplan:

```bash
sudo netplan generate
```

Если команда ничего не выводит — это хороший знак.  
Значит синтаксис корректный.

Применить настройки:

```bash
sudo netplan apply
```

Безопасное применение с возможностью отката:

```bash
sudo netplan try
```

---

### 10. Права на netplan-файл

После создания netplan-файла может появиться предупреждение:

```text
Permissions for /etc/netplan/50-lab-network.yaml are too open.
```

Это значит, что файл сетевой конфигурации доступен слишком широко.

Исправление:

```bash
sudo chmod 600 /etc/netplan/50-lab-network.yaml
```

Смысл `chmod 600`:

```text
читать и изменять файл может только владелец/root
остальные пользователи не имеют доступа
```

Почему это важно:

```text
сетевые конфиги не должны быть доступны всем пользователям
```

---

### 11. Если SSH не работает

Если при подключении:

```powershell
ssh germanix@192.168.56.101
```

появляется ошибка:

```text
Connection timed out
```

это обычно проблема сети, а не пароля.

Если пароль неправильный, чаще будет ошибка типа:

```text
Permission denied
```

`Connection timed out` означает:

```text
Windows не может достучаться до Ubuntu по сети
```

Порядок диагностики:

1. Проверить, включена ли Ubuntu VM.
2. Проверить, есть ли IP `192.168.56.101/24` на `enp0s8`.
3. Проверить ping из Windows:

```powershell
ping 192.168.56.101 -n 4
```

4. Проверить SSH-сервис внутри Ubuntu:

```bash
systemctl status ssh --no-pager
```

5. Если SSH не запущен, запустить:

```bash
sudo systemctl start ssh
```

6. Проверить, слушает ли порт 22:

```bash
sudo ss -tulpn | grep :22
```

7. Проверить firewall:

```bash
sudo ufw status
```

8. Если SSH недоступен, зайти через VirtualBox-консоль и восстановить сеть вручную.

---

### 12. Временное восстановление IP

Если SSH не работает, а у `enp0s8` нет IP `192.168.56.101/24`, нужно зайти через VirtualBox-консоль и временно назначить IP:

```bash
sudo ip link set enp0s8 up
sudo ip addr add 192.168.56.101/24 dev enp0s8
ip -br addr show enp0s8
```

Если появляется сообщение:

```text
Address already assigned
```

это не ошибка.

Это значит:

```text
IP уже назначен
```

---

### 13. VirtualBox-консоль и SSH

VirtualBox-консоль — аварийный доступ.

Она нужна, если:

- сломалась сеть
- пропал IP
- SSH не работает
- netplan настроен неправильно
- нужно восстановить доступ вручную

SSH — основной рабочий доступ.

Он нужен для нормального удалённого администрирования Linux-сервера по сети.

Коротко:

```text
VirtualBox-консоль = аварийный доступ
SSH = основной рабочий доступ
```

## 12) Linux 2.1: ориентация на сервере

### Цель блока

Научиться после подключения к Linux-серверу быстро понимать:

- под каким пользователем я работаю
- на каком сервере нахожусь
- в какой папке нахожусь
- где моя домашняя папка
- какие файлы и папки находятся рядом

Главная логика процесса:

```text
подключился к серверу → понял кто я → понял где я → посмотрел окружение
```

Это базовый процесс перед любой работой в Linux.

Если я не понимаю, где нахожусь и под каким пользователем работаю, я могу выполнить команду не там, изменить не тот файл или сломать конфигурацию.

---

### Основная рабочая строка Linux

Если я вижу:

```bash
germanix@ubuntuserver1:~$
```

это означает:

```text
germanix = текущий пользователь
ubuntuserver1 = имя сервера
~ = домашняя папка текущего пользователя
$ = обычный пользователь, не root
```

Если вместо `$` был бы символ `#`, это означало бы, что я работаю под root.

---

### Команды ориентации

#### 1. Текущий пользователь

```bash
whoami
```

Показывает, под каким пользователем я сейчас работаю.

Пример результата:

```text
germanix
```

Смысл:

```text
Я работаю как обычный пользователь germanix, а не как root.
```

---

#### 2. Имя сервера

```bash
hostname
```

Показывает имя сервера.

Пример результата:

```text
ubuntuserver1
```

Смысл:

```text
Я понимаю, на какой машине сейчас нахожусь.
```

Это важно, потому что в реальной инфраструктуре может быть много серверов: GitLab-сервер, runner-сервер, сервер мониторинга, тестовая VM и так далее.

---

#### 3. Текущая папка

```bash
pwd
```

`pwd` расшифровывается как:

```text
print working directory
```

Команда показывает полный путь до текущей рабочей папки.

Пример результата:

```text
/home/germanix
```

Смысл:

```text
Я понимаю, где сейчас нахожусь в файловой системе Linux.
```

---

#### 4. Домашняя папка пользователя

```bash
echo $HOME
```

Показывает домашнюю папку текущего пользователя.

Пример результата:

```text
/home/germanix
```

`$HOME` — это переменная окружения, в которой хранится путь к домашней папке пользователя.

---

#### 5. Обычный список файлов

```bash
ls
```

Показывает обычное содержимое текущей папки.

Пример результата:

```text
linux-lab
```

Смысл:

```text
Я вижу обычные файлы и папки, которые находятся в текущей директории.
```

---

#### 6. Подробный список файлов

```bash
ls -la
```

Показывает подробное содержимое текущей папки, включая скрытые файлы.

Флаги:

```text
-l = long format, подробный вывод
-a = all, показать все файлы, включая скрытые
```

`ls -la` показывает:

- права доступа
- количество ссылок
- владельца
- группу
- размер
- дату изменения
- имя файла или папки
- скрытые файлы

---

### Домашняя папка

Домашняя папка пользователя `germanix`:

```text
/home/germanix
```

Символ:

```text
~
```

означает домашнюю папку текущего пользователя.

Для пользователя `germanix`:

```text
~ = /home/germanix
```

Поэтому строка:

```bash
germanix@ubuntuserver1:~$
```

означает, что я нахожусь в домашней папке пользователя `germanix`.

---

### Скрытые файлы

Файлы и папки, которые начинаются с точки, считаются скрытыми.

Примеры:

```text
.bash_history
.bashrc
.profile
.ssh
.config
.cache
```

Обычная команда:

```bash
ls
```

может их не показывать.

Команда:

```bash
ls -la
```

показывает скрытые файлы и папки.

---

### Что означают `.` и `..`

В выводе `ls -la` есть специальные обозначения:

```text
.  = текущая папка
.. = папка уровнем выше
```

Если текущая папка:

```text
/home/germanix
```

то:

```text
.  = /home/germanix
.. = /home
```

Это важно для понимания перемещения по файловой системе.

---

### Частые ошибки

#### Ошибка 1: опечатка в команде

Неправильно:

```bash
woami
```

Правильно:

```bash
whoami
```

Linux очень буквальный: если команда введена с ошибкой, она не выполнится.

---

#### Ошибка 2: попытка очистить экран командой `c`

Неправильно:

```bash
c
```

Правильно:

```bash
clear
```

Команда `clear` очищает экран терминала.

---

#### Ошибка 3: попытка выйти из SSH командой `disconnect`

Неправильно:

```bash
disconnect
```

Правильно:

```bash
exit
```

или:

```text
Ctrl + D
```

Команда `exit` завершает текущую SSH-сессию и возвращает меня обратно в Windows PowerShell.

---

### Как правильно выйти из SSH

Если я нахожусь внутри Ubuntu через SSH и хочу выйти обратно в Windows PowerShell, использую:

```bash
exit
```

или:

```text
Ctrl + D
```

После выхода я снова увижу строку Windows PowerShell вида:

```powershell
PS C:\Users\Герман>
```

### Критерий понимания блока

1. Что показывает `whoami`

3. Что показывает `pwd`
4. Что означает символ `~`

8. Как правильно выйти из SSH-сессии
9. Почему перед работой на сервере нужно понимать текущий контекст

Команда читается так:

```text
скопируй note.txt в note-copy.txt
```

Это означает:

Стало:




`-r` означает `recursive`.

Смысл:

```text
удалить папку вместе со всем содержимым внутри
```

### Почему `rm` опасен

В Linux команда `rm` обычно удаляет без корзины.

В Windows файл часто можно восстановить из корзины.

В Linux после `rm` файл может исчезнуть сразу.

Поэтому перед `rm` всегда нужно проверять:

```bash
pwd
ls -la
```

---

### Правило перед `rm`, `cp`, `mv`

Перед командами:

```bash
rm
cp
mv
```

нужно выполнить:

```bash
pwd
ls -la
```

Зачем:

```text
pwd показывает, где я нахожусь.
ls -la показывает, какие файлы и папки реально есть.
```

Это нужно, чтобы не удалить, не скопировать и не переместить не тот файл.

Главное правило:

```text
Сначала понять контекст, потом выполнять действие.
```


Из-за этого команда может не выполниться.

Решение:

```text

```

```bash
tail app.log
```

```text
tail нужен, чтобы быстро посмотреть последние события в файле.
```

Найти информационные строки:

### Поиск файлов и папок через find

`find` ищет файлы и папки в файловой системе.

```text
grep ищет строки внутри файла.
find ищет файлы и папки.
```

Найти файл `app.log` от текущей папки:

```bash
find . -name "app.log"
```

Найти все `.log` файлы:

```bash
find . -name "*.log"
```

Найти все `.txt` файлы:

```bash
find . -name "*.txt"
```

Найти всё, где в имени есть `note`:

```bash
find . -name "*note*"
```

Показать только файлы:

```bash
find . -type f
```

Показать только папки:

```bash
find . -type d
```

```bash
find ~/linux-lab -name "app.log"
```

```text
-type f = искать только файлы
-type d = искать только папки
*       = любые символы
```

Пример:

```bash
find . -name "*.log"
```

означает:

```text

```

### Что показывает ls -la

```text

│            │   │          │          │     └──────────────── дата изменения
│            │   │          │          └────────────────────── размер в байтах
│            │   │          └───────────────────────────────── группа
│            │   └──────────────────────────────────────────── владелец
│            └──────────────────────────────────────────────── количество жёстких ссылок
└───────────────────────────────────────────────────────────── тип объекта и права
```

Первый символ показывает тип объекта:

```text
- = обычный файл
d = директория / папка
```

Примеры:

```text
-rw-r--r-- = обычный файл
drwxr-xr-x = директория
```

Число после прав:

```text
-rw-r--r-- 1 germanix germanix app.log
```

`1` — это количество жёстких ссылок. Для обычного файла чаще всего будет `1`. Для папок может быть `2` и больше.

На текущем этапе важно запомнить:

```text
число после прав — это не права, не владелец и не размер.
Это отдельное поле ls -la.
```

---

### Owner, group, others

Linux делит доступ к файлу или папке на три группы:

```text
owner  = владелец
group  = группа
others = остальные пользователи
```

Пример:

```text
-rw-r--r--
```

Разбор:

```text
-   rw-   r--   r--
│    │     │     │
│    │     │     └── others / остальные
│    │     └──────── group / группа
│    └────────────── owner / владелец
└─────────────────── тип объекта
```

Для файла `app.log`:

```text
-rw-r--r-- 1 germanix germanix app.log
```

означает:

```text
тип объекта: обычный файл
владелец: germanix
группа: germanix
права владельца: rw-
права группы: r--
права остальных: r--
```

---

### Что означают r, w, x

Базовые права:

```text
r = read    = читать
w = write   = писать / изменять
x = execute = выполнять
```

Для файла:

```text
r = можно прочитать файл
w = можно изменить файл
x = можно выполнить файл как программу или скрипт
```

Для папки:

```text
r = можно увидеть список файлов внутри
w = можно создавать, удалять и переименовывать внутри
x = можно зайти в папку через cd
```

Критически важное отличие:

```text
x для файла = выполнить файл
x для папки = зайти внутрь папки
```

Пример:

```bash
cd archive
```

Чтобы зайти в папку, на неё нужно право `x`.

---

### Числовые права chmod

`chmod` меняет права доступа к файлу или папке.

```text
chmod = change mode
```

Каждому праву соответствует число:

```text
r = 4
w = 2
x = 1
```

Одна цифра получается сложением нужных прав:

```text
0 = --- = нет прав
1 = --x = только выполнение
2 = -w- = только запись
3 = -wx = запись + выполнение
4 = r-- = только чтение
5 = r-x = чтение + выполнение
6 = rw- = чтение + запись
7 = rwx = чтение + запись + выполнение
```

Главная таблица:

```text
7 = rwx = 4 + 2 + 1
6 = rw- = 4 + 2
5 = r-x = 4 + 1
4 = r-- = 4
0 = --- = нет прав
```

---

### Почему chmod использует три цифры

Формат:

```bash
chmod XYZ file
```

Где:

```text
X = права владельца
Y = права группы
Z = права остальных
```

Пример:

```bash
chmod 644 app.log
```

Расшифровка:

```text
6 = владелец: rw-
4 = группа: r--
4 = остальные: r--
```

Итог:

```text
644 = rw-r--r--
```

То есть:

```text
владелец может читать и изменять файл
группа может только читать
остальные могут только читать
```

---

### Главные режимы

#### chmod 600

```text
600 = rw-------
```

Разбор:

```text
6 = владелец: читать + писать
0 = группа: нет прав
0 = остальные: нет прав
```

Смысл:

```text
только владелец может читать и изменять файл
никто другой не имеет доступа
```

Применение:

```text
SSH-ключи
секреты
файлы с паролями
чувствительные конфиги
```

Пример:

```bash
chmod 600 private.key
```

---

#### chmod 644

```text
644 = rw-r--r--
```

Разбор:

```text
6 = владелец: читать + писать
4 = группа: читать
4 = остальные: читать
```

Смысл:

```text
владелец может читать и изменять
группа и остальные могут только читать
```

Применение:

```text
обычные файлы
логи
конфиги
документация
```

Пример:

```bash
chmod 644 app.log
```

---

#### chmod 755

```text
755 = rwxr-xr-x
```

Разбор:

```text
7 = владелец: читать + писать + выполнять
5 = группа: читать + выполнять
5 = остальные: читать + выполнять
```

Смысл:

```text
владелец может всё
группа и остальные могут читать и выполнять
но не могут изменять
```

Применение:

```text
скрипты
исполняемые файлы
папки
```

Пример:

```bash
chmod 755 deploy.sh
```

После этого скрипт можно попытаться запустить:

```bash
./deploy.sh
```

Важно:

```text
право x не превращает любой текстовый файл в рабочую программу.
Оно только разрешает системе попытку выполнить файл.
```

### Практика chmod

Рабочая папка:

```bash
cd ~/linux-lab/files-practice
```

Создание тестового файла:

```bash

echo "permissions test" > permissions-demo.txt
```

Проверка стартовых прав:

```bash

```

У меня стартовые права были:

```text
-rw-rw-r-- permissions-demo.txt
```

Это:

```text
664 = rw-rw-r--
```

То есть:

```text
владелец: читать + писать
группа: читать + писать
остальные: читать
```

Стартовые права могут отличаться в зависимости от настроек системы. Главное — `chmod` принудительно выставляет нужный режим.


### chown

`chown` меняет владельца и/или группу файла.

```text
chown = change owner
```

Главная разница:

```text
chmod = меняет права
chown = меняет владельца и группу
```

Пример строки:

```text
-rw-r--r-- 1 germanix germanix app.log
```

Здесь:

```text
права: rw-r--r--
владелец: germanix
группа: germanix
```

Команда:

```bash
sudo chown root:root app.log
```

означает:

```text
владелец станет root
группа станет root
```

То есть:

```text
root:root
│    │
│    └── группа
└─────── владелец
```

Команда:

```bash
sudo chown germanix:germanix app.log
```

возвращает:

```text
владелец = germanix
группа = germanix
```

---

### sudo

`sudo` позволяет выполнить команду с повышенными правами, обычно от имени `root`.

Примеры:

```bash
sudo chown root:root file
sudo chmod 600 file
sudo apt update
sudo systemctl restart ssh
```

Важно:

```text
sudo не нужно использовать бездумно.
sudo даёт больше прав, значит ошибочная команда может нанести больше вреда.
```

Правильная логика:

```text
обычные действия выполняю как germanix
административные действия выполняю через sudo
перед sudo понимаю, что команда делает
```

---

### Практика chown и Permission denied

Файл сначала принадлежал пользователю `germanix`:

```text
-rwxr-xr-x 1 germanix germanix permissions-demo.txt
```

Команда:

```bash
sudo chown root:root permissions-demo.txt
```

изменила владельца и группу:

```text
-rwxr-xr-x 1 root root permissions-demo.txt
```

После этого команда:

```bash
echo "second line" >> permissions-demo.txt
```

дала ошибку:

```text
Permission denied
```

Почему:

```text
файл принадлежит root
текущий пользователь germanix больше не владелец
при правах 755 писать может только владелец
для группы и остальных есть только r-x
права w для germanix нет
```

Возврат владельца:

```bash
sudo chown germanix:germanix permissions-demo.txt
chmod 644 permissions-demo.txt
```

После этого запись снова прошла:

```bash
echo "second line" >> permissions-demo.txt
cat permissions-demo.txt
```

Результат:

```text
permissions test
second line
```

### Алгоритм при Permission denied

Если вижу ошибку:

```text

```

проверяю:

```bash
pwd
whoami
ls -la
id
groups
```

Логика диагностики:

```text
1. Где я нахожусь?
2. Кто я?
3. Какие права у файла/папки?
4. Кто владелец?
5. Какая группа?
6. Есть ли у моего пользователя нужное право r/w/x?
7. Нужен ли sudo?
8. Безопасно ли применять sudo?
```

### Что нужно уметь объяснить

1. Что показывает `ls -la`
2. Что значит первый символ `-`
3. Что значит первый символ `d`
4. На какие 3 группы делятся права
5. Что означают `r`, `w`, `x` для файла
6. Что означает `x` для папки

15. Что такое `sudo`

### Главный вывод

Права и владельцы — это базовый механизм безопасности Linux.

Коротко:

### Почему понадобился hash -r

После удаления `tree` была ситуация:

```bash
command -v tree
```

всё ещё показывал:

```text
/usr/bin/tree
```

Хотя пакет уже был удалён.

Причина:

```text
Bash может запоминать путь к ранее найденной команде,
чтобы не искать её каждый раз заново.
```

Для сброса этого кеша используется:

```bash
hash -r
```

После этого проверка стала корректной:

```bash
command -v tree || echo "tree is not installed"
ls -l /usr/bin/tree || echo "/usr/bin/tree file is gone"
```

Ожидаемый результат:

```text
tree is not installed
ls: cannot access '/usr/bin/tree': No such file or directory
/usr/bin/tree file is gone
```

Главная мысль:

```text
если пакет удалён, но shell как будто помнит старый путь,
можно выполнить hash -r и проверить заново
```

```text
1 строка Listing... Done
19 строк пакетов
```

Чтобы увидеть 20 пакетов, можно взять 21 строку:

```bash
apt list --installed | head -n 21
```

Или убрать первую служебную строку:

```bash
apt list --installed | tail -n +2 | head -n 20
```

Разбор:

```text
tail -n +2 = начать вывод со второй строки
head -n 20 = показать первые 20 строк после этого
```

---

### grep

Команда:

```bash
apt list --installed | grep openssh
```

означает:

```text
взять полный список установленных пакетов
и оставить только строки, где есть openssh
```

Важно:

```text
grep ищет по всему выводу,
если перед ним не было head
```

Разница:

```bash
apt list --installed | head -n 20 | grep openssh
```

означает:

```text
сначала взять первые 20 строк,
потом искать openssh только среди них
```

А команда:

```bash
apt list --installed | grep openssh | head -n 20
```

означает:

```text
сначала найти openssh во всём списке,
потом показать первые 20 совпадений
```

Порядок команд в pipe важен.

---

### Оператор ||

Команда:

```bash
apt list --installed | grep tree || echo "tree package is not installed"
```

`||` означает:

```text
если команда слева завершилась неуспешно,
выполнить команду справа
```

В этом примере:

```text
если grep tree ничего не нашёл,
вывести сообщение tree package is not installed
```

`echo` просто печатает текст в терминал.

---

### apt list --installed

Команда:

```bash
apt list --installed
```

показывает установленные пакеты.

Чтобы не выводить огромный список:

```bash
apt list --installed | head -n 20
```

Чтобы найти конкретный пакет:

```bash
apt list --installed | grep bash
apt list --installed | grep openssh
apt list --installed | grep tree || echo "tree package is not installed"
```

Примеры выводов:

```text
bash/noble,now 5.2.21-2ubuntu4 amd64 [installed]
bash-completion/noble,now 1:2.11-8 all [installed,automatic]
```

Смысл:

```text
[installed] = пакет установлен
[installed,automatic] = пакет установлен автоматически, обычно как зависимость
```

### OpenSSH-пакеты

показала:

```text

```

Смысл:

```text
openssh-client = SSH-клиент
openssh-server = SSH-сервер
openssh-sftp-server = SFTP через SSH
```

Для нашей Ubuntu VM особенно важен:

```text
openssh-server
```

### apt upgrade --simulate

Команда:

```bash
apt upgrade --simulate
```

показывает, что сделал бы `apt upgrade`, но без реального изменения системы.

Смысл:

```text
безопасно посмотреть план обновления
```

В выводе можно увидеть:

```text
потом принимаю решение
```

### dpkg

`dpkg` — низкоуровневый инструмент для работы с Debian-пакетами.

Главная разница:

```text
apt = высокий уровень, удобный менеджер пакетов
dpkg = нижний уровень, база и управление .deb-пакетами
```

Обычно:

```text
для обычной установки и удаления использую apt
для проверки состояния пакета на низком уровне использую dpkg
```

---

### dpkg -l

Команда:

```bash
dpkg -l
```

показывает список пакетов из базы `dpkg`.

Чтобы ограничить вывод:

```bash
dpkg -l | head -n 20
```

Чтобы найти пакет:

```bash
dpkg -l | grep bash
dpkg -l | grep openssh
dpkg -l | grep tree || echo "tree package is not installed in dpkg"
```

В выводе строки могут начинаться с:

```text
ii
```

Для нашего уровня:

```text
ii = пакет установлен нормально
```

Более точно:

```text
первая i = пакет выбран для установки
вторая i = пакет установлен
```

---

### apt vs dpkg

Короткая формула:

```text
apt = работаю с пакетами
dpkg = проверяю/чиню пакетную базу и работаю с .deb напрямую
```

Использую `apt`, когда нужно:

```text
найти пакет
посмотреть информацию о пакете
установить пакет
удалить пакет
обновить список пакетов
посмотреть доступные обновления
посмотреть план upgrade
```

Команды:

```bash
apt search nginx
apt show nginx
sudo apt install nginx
sudo apt remove nginx
sudo apt update
apt list --upgradable
apt upgrade --simulate
```

Использую `dpkg`, когда нужно:

```text
проверить состояние пакета на низком уровне
посмотреть статус конкретного пакета
установить локальный .deb файл
```

Команды:

```bash
dpkg -l | grep nginx
dpkg -s nginx
sudo dpkg -i package.deb
```

Главная мысль:

```text
для обычной работы — apt
для диагностики и низкого уровня — dpkg
```

### Команды блока

```bash
sudo apt update

apt search tree
apt show tree

command -v tree || echo "tree is not installed"

sudo apt install -y tree

command -v tree
tree --version
tree ~/linux-lab -L 2

sudo apt remove -y tree

hash -r
command -v tree || echo "tree is not installed"
ls -l /usr/bin/tree || echo "/usr/bin/tree file is gone"

apt list --installed | head -n 20
apt list --installed | grep bash
apt list --installed | grep openssh
apt list --installed | grep tree || echo "tree package is not installed"

apt list --upgradable | head -n 20
apt upgrade --simulate | head -n 40

dpkg -l | grep bash
dpkg -l | grep openssh
dpkg -l | grep tree || echo "tree package is not installed in dpkg"
```

### Что нужно уметь объяснить

1. Что делает `sudo apt update`
2. Чем `apt update` отличается от `apt upgrade`
3. Что делает `apt show tree`
4. Что делает `command -v tree`
5. Что такое команда в Linux
6. Что означает `||`
7. Что делает `sudo apt install -y tree`
8. Что делает `sudo apt remove -y tree`
9. Зачем нужен `hash -r`
10. Что делает `apt list --installed | grep openssh`
11. Почему `openssh` мог не попасть в первые 20 строк, но нашёлся через `grep`
12. Что значит `[installed]`
13. Что значит `[installed,automatic]`
14. Что делает `apt list --upgradable`
15. Что делает `apt upgrade --simulate`
16. Чем отличается `apt` от `dpkg`
17. Что значит `ii` в `dpkg -l`

---

### Главный вывод

`apt` нужен для обычной работы с пакетами:

```text
найти → посмотреть → установить → проверить → удалить → проверить
```

`dpkg` нужен для низкоуровневой проверки состояния пакетов.

При работе с пакетами важно не просто запускать команды, а понимать процесс:

```text
1. Что я хочу установить?
2. Есть ли такой пакет?
3. Что это за пакет?
4. Установлен ли он уже?
5. Появилась ли команда после установки?
6. Работает ли команда?
7. Удалился ли пакет после remove?
8. Не держит ли Bash старый путь в кеше?
```

## 17) Linux 2.6: systemctl, сервисы и автозапуск

### Цель блока

Научиться работать с сервисами Linux через `systemctl`:

```text
посмотреть статус сервиса
понять, работает ли сервис сейчас
запустить сервис
остановить сервис
перезапустить сервис
проверить автозапуск
включить автозапуск
отключить автозапуск
отличать active от enabled
```

Это важно для DevOps, потому что серверные приложения обычно работают как фоновые сервисы:

```text
ssh — принимает SSH-подключения
nginx — веб-сервер / reverse proxy
docker — Docker daemon
postgresql — база данных
gitlab-runner — выполняет GitLab CI/CD jobs
```

Если сервис “не работает”, один из первых шагов диагностики:

```bash
systemctl status service
```

---

### Что такое сервис

Сервис — это программа, которая работает в фоне.

Пользователь не запускает её вручную каждый раз в терминале. Обычно сервис запускается системой и продолжает работать самостоятельно.

Примеры:

```text
ssh.service
nginx.service
docker.service
cron.service
systemd-journald.service
```

Коротко:

```text
сервис = фоновая программа, которой управляет systemd
```

---

### systemctl

`systemctl` — команда для управления systemd и его unit-ами.

В нашем блоке нас интересуют service units, то есть сервисы.

Главные команды:

```bash
systemctl status service
systemctl is-active service
systemctl is-enabled service

sudo systemctl start service
sudo systemctl stop service
sudo systemctl restart service

sudo systemctl enable service
sudo systemctl disable service
```

---

### Почему используется sudo

Просмотр статуса обычно можно делать без `sudo`:

```bash
systemctl status nginx
systemctl is-active nginx
systemctl is-enabled nginx
```

Но управление системным сервисом требует повышенных прав:

```bash
sudo systemctl start nginx
sudo systemctl stop nginx
sudo systemctl restart nginx
sudo systemctl enable nginx
sudo systemctl disable nginx
```

Причина:

```text
старт, остановка и автозапуск системных сервисов влияют на работу всей системы
```

---

### systemctl status

Команда:

```bash
systemctl status ssh --no-pager
```

или:

```bash
systemctl status nginx --no-pager
```

показывает подробное состояние сервиса.

Важные строки:

```text
Loaded:
Active:
Main PID:
Tasks:
Memory:
CGroup:
```

Самая важная строка:

```text
Active:
```

Пример:

```text
Active: active (running)
```

означает:

```text
сервис сейчас запущен и работает
```

Пример:

```text
Active: inactive (dead)
```

означает:

```text
сервис сейчас остановлен
```

---

### --no-pager

Команда:

```bash
systemctl status nginx
```

может открыть вывод через pager, например `less`.

Pager — это просмотрщик длинного вывода.

В pager выход:

```text
q
```

Команда:

```bash
systemctl status nginx --no-pager
```

означает:

```text
не открывать pager, вывести результат сразу в терминал
```

Если вывод короткий, разницы можно не заметить.

Но в обучении удобно использовать `--no-pager`, чтобы не застрять в просмотрщике.

---

### Проверка SSH-сервиса

Подключение к Ubuntu выполняется с Windows:

```powershell
ssh germanix@192.168.56.101
```

На Ubuntu это подключение принимает сервис:

```text
ssh.service
```

Проверка:

```bash
systemctl status ssh --no-pager
systemctl is-active ssh
systemctl is-enabled ssh
```

Если:

```text
Active: active (running)
```

значит SSH-сервис работает сейчас.

Если:

```text
enabled
```

значит SSH включён в автозапуск при старте системы.

Схема:

```text
Windows PowerShell
        |
        | ssh germanix@192.168.56.101
        v
Ubuntu Server
        |
        v
ssh.service принимает подключение
```

---

### Почему не тренировать stop на SSH

Если выполнить:

```bash
sudo systemctl stop ssh
```

то остановится сервис, который принимает SSH-подключения.

Возможные последствия:

```text
новые SSH-подключения не будут приниматься
текущая SSH-сессия может оборваться
можно потерять удалённый доступ к серверу
```

Это не ломает сервер навсегда, но может выбить из SSH.

Восстановление через VirtualBox-консоль:

```bash
sudo systemctl start ssh
systemctl status ssh --no-pager
```

Поэтому для тренировки безопаснее использовать `nginx`.

```bash
systemctl is-enabled nginx
```

```bash

```


Запустить сервис:

```bash

```

Проверить:

```bash

```

Ожидаемо:

```text

```


Проверить:

```bash

```

### start, stop, restart

Коротко:

```text
start   = запустить сервис сейчас
stop    = остановить сервис сейчас
restart = остановить и сразу запустить заново
```

Примеры:

```bash
sudo systemctl start nginx
sudo systemctl stop nginx
sudo systemctl restart nginx
```

`restart` часто используется после изменения конфигурации сервиса.

Например:

```text
изменили nginx-конфиг
проверили конфиг
перезапустили nginx
проверили статус
```

---

### is-active

Команда:

```bash
systemctl is-active nginx
```

проверяет, работает ли сервис прямо сейчас.

Возможные результаты:

```text
active
inactive
failed
unknown
```

Для нашего базового уровня:

```text
active = работает сейчас
inactive = не работает сейчас
failed = сервис упал или не смог стартовать
```

---

### is-enabled

Команда:

```bash
systemctl is-enabled nginx
```

проверяет, включён ли автозапуск сервиса при старте системы.

Возможные результаты:

```text
enabled
disabled
static
```

Для нашего базового уровня:

```text
enabled = включён в автозапуск
disabled = не включён в автозапуск
static = нельзя включить напрямую обычным enable или нет секции Install
```

---

### active vs enabled

Это главный смысл блока.

Есть два разных вопроса:

```text
1. Работает ли сервис прямо сейчас?
2. Запустится ли сервис после перезагрузки?
```

Для первого:

```bash
systemctl is-active nginx
```

Для второго:

```bash
systemctl is-enabled nginx
```

Таблица:

```text
active + enabled
сервис работает сейчас и включён в автозапуск

active + disabled
сервис работает сейчас, но после перезагрузки сам не стартует

inactive + enabled
сервис сейчас остановлен, но после перезагрузки стартует

inactive + disabled
сервис сейчас остановлен и в автозапуск не включён
```

Коротко:

```text
active/inactive = состояние сейчас
enabled/disabled = автозапуск
```

---

### enable и disable

Команда:

```bash
sudo systemctl disable nginx
```

отключает автозапуск.

Важно:

```text
disable не обязан останавливать сервис прямо сейчас
```

Практический пример:

```bash
sudo systemctl disable nginx
systemctl is-enabled nginx
systemctl is-active nginx
```

Результат:

```text
disabled
active
```

Это значит:

```text
nginx работает сейчас,
но после перезагрузки сам не запустится
```

Команда:

```bash
sudo systemctl enable nginx
```

включает автозапуск.

Проверка:

```bash
systemctl is-enabled nginx
systemctl is-active nginx
```

Результат:

```text
enabled
active
```

Это значит:

```text
nginx работает сейчас
и включён в автозапуск
```

## 18) Linux 2.7: journalctl и диагностика логов сервисов

### Цель блока

Научиться читать логи сервисов через `journalctl` и использовать их для диагностики.

Главная связка:

```text
systemctl status service
показывает состояние сервиса сейчас

journalctl -u service
показывает логи сервиса
```

Если сервис не работает, правильный путь диагностики:

```text
1. systemctl status service
2. journalctl -u service
3. найти ошибку
4. исправить причину
5. проверить конфиг, если это сервис с конфигом
6. restart/start service
7. снова проверить status и logs
```

---

### Что такое journalctl

`journalctl` — команда для просмотра журнала systemd.

Журнал содержит записи о:

```text
запуске сервисов
остановке сервисов
ошибках сервисов
SSH-подключениях
системных событиях
загрузке системы
работе systemd units
```

Коротко:

```text
journalctl = читать системные логи systemd
```

---

### systemctl vs journalctl

`systemctl` и `journalctl` решают разные задачи.

```text
systemctl status service
отвечает на вопрос:
что с сервисом сейчас?

journalctl -u service
отвечает на вопрос:
что происходило с сервисом в логах?
```

Пример:

```bash
systemctl status nginx --no-pager
journalctl -u nginx -n 20 --no-pager
```

Смысл:

```text
сначала смотрю состояние сервиса,
потом смотрю последние записи лога этого сервиса
```

---

### Базовая команда journalctl для сервиса

Команда:

```bash
journalctl -u nginx --no-pager
```

Разбор:

```text
journalctl = открыть журнал systemd
-u nginx = показать записи только по unit/service nginx
--no-pager = вывести сразу в терминал, без less/pager
```

Важно:

```text
-u nginx — это фильтр по сервису/unit.
Это не “логи nginx” само по себе, а указание journalctl:
покажи только записи, связанные с nginx.
```

Для SSH:

```bash
journalctl -u ssh --no-pager
```

Для nginx:

```bash
journalctl -u nginx --no-pager
```

---

### Ограничение количества строк: -n

Команда:

```bash
journalctl -u nginx -n 20 --no-pager
```

означает:

```text
показать последние 20 строк логов nginx
```

Разбор:

```text
-u nginx = только unit/service nginx
-n 20 = последние 20 записей
--no-pager = без просмотрщика
```

Важно:

```text
-n 20 показывает последние 20 строк,
а не первые.
```

Это удобно, потому что в логах обычно самые свежие события находятся в конце.

---

### Логи текущей загрузки: -b

Команда:

```bash
journalctl -u nginx -b --no-pager
```

означает:

```text
показать логи nginx за текущую загрузку системы
```

Разбор:

```text
-u nginx = только nginx
-b = текущая загрузка системы
--no-pager = без просмотрщика
```

Чтобы не выводить слишком много строк:

```bash
journalctl -u nginx -b --no-pager | tail -n 20
```

Разбор:

```text
journalctl -u nginx -b --no-pager = все логи nginx за текущую загрузку
| tail -n 20 = показать последние 20 строк
```

---

### Логи по времени: --since

Команда:

```bash
journalctl -u nginx --since "1 hour ago" --no-pager
```

означает:

```text
показать логи nginx за последний час
```

Если вывод:

```text
-- No entries --
```

это значит:

```text
за выбранный период записей нет
```

Это не ошибка. Просто за указанный период сервис не писал новых записей в журнал.

---

### Логи в реальном времени: -f

Команда:

```bash
journalctl -u nginx -f --no-pager
```

означает:

```text
следить за логами nginx в реальном времени
```

Разбор:

```text
-u nginx = только unit/service nginx
-f = follow, ждать новые записи и сразу показывать их
--no-pager = без просмотрщика
```

Важно:

```text
journalctl -f не завершается сам.
Он ждёт новые записи.
```

Выход:

```text
Ctrl+C
```

---

### Почему для -f нужны две SSH-сессии

Если в одном окне запустить:

```bash
journalctl -u nginx -f --no-pager
```

это окно будет занято просмотром логов.

В этом же окне не нужно вводить обычные shell-команды, пока работает `-f`.

Правильная схема:

```text
1 окно:
journalctl -u nginx -f --no-pager

2 окно:
sudo systemctl restart nginx
systemctl is-active nginx

1 окно:
видим новые строки логов

выход из -f:
Ctrl+C
```

После перезапуска nginx в первом окне появляются новые записи:

```text
Stopping nginx.service
nginx.service: Deactivated successfully.
Stopped nginx.service
Starting nginx.service
Started nginx.service
```

Главная мысль:

```text
journalctl -f позволяет наблюдать событие в моменте
```

---

### SSH-логи

Команда:

```bash
journalctl -u ssh -n 20 --no-pager
```

показывает последние SSH-события.

Пример строки:

```text
Accepted password for germanix from 192.168.56.1 port 58106 ssh2
```

Смысл:

```text
пользователь germanix успешно вошёл по SSH
с адреса 192.168.56.1
```

В нашей лаборатории:

```text
192.168.56.1 = Windows Host-Only adapter
192.168.56.101 = Ubuntu Server
```

Схема:

```text
Windows PowerShell
192.168.56.1
        |
        | ssh germanix@192.168.56.101
        v
Ubuntu Server
192.168.56.101
```

Строка:

```text
pam_unix(sshd:session): session opened for user germanix
```

означает:

```text
для пользователя germanix открыта SSH-сессия
```

---

### Nginx-логи

Команда:

```bash
journalctl -u nginx -n 20 --no-pager
```

показывает последние события nginx.

Типовые строки:

```text
Starting nginx.service
Started nginx.service
Stopping nginx.service
Stopped nginx.service
nginx.service: Deactivated successfully.
```

Смысл:

```text
Starting = systemd начал запуск nginx
Started = nginx успешно запущен
Stopping = systemd начал остановку nginx
Stopped = nginx остановлен
Deactivated successfully = nginx успешно деактивирован
```

Связка:

```text
sudo systemctl restart nginx
        ↓
journalctl -u nginx показывает:
Stopping → Stopped → Starting → Started
```

---

### Диагностика ошибки nginx

Был создан специально неправильный конфиг:

```bash
sudo tee /etc/nginx/conf.d/broken-lab.conf > /dev/null <<'EOF'
server {
    listen 8080
    server_name broken.local;
}
EOF
```

Ошибка:

```text
listen 8080
```

В nginx-конфиге после директивы нужна точка с запятой:

```text
listen 8080;
```

Проверка конфига:

```bash
sudo nginx -t
```

Ожидаемо при ошибке nginx сообщает, что конфигурация неправильная.

---

### Почему сначала nginx -t, а потом restart

Правильная привычка:

```text
сначала проверить конфиг,
потом перезапускать сервис
```

Команда:

```bash
sudo nginx -t
```

проверяет конфигурацию nginx.

Если конфиг исправен:

```text
syntax is ok
test is successful
```

Если конфиг сломан, `nginx -t` покажет ошибку и проблемный файл.

---

### Что делать, если nginx не стартует

Правильная цепочка:

```bash
systemctl status nginx --no-pager
journalctl -u nginx -n 30 --no-pager
sudo nginx -t
```

Дальше:

```text
1. найти ошибку
2. исправить или удалить плохой конфиг
3. снова проверить nginx -t
4. перезапустить сервис nginx
5. проверить статус
6. проверить последние логи
```

В нашей практике плохой файл удалялся так:

```bash
sudo rm /etc/nginx/conf.d/broken-lab.conf
```

Проверка:

```bash
sudo nginx -t
```

Если всё нормально:

```bash
sudo systemctl restart nginx
systemctl status nginx --no-pager
journalctl -u nginx -n 20 --no-pager
```

---

### Важный вывод из практики

Если сервис уже в состоянии `failed`, недостаточно просто исправить файл.

Нужно после исправления снова запустить или перезапустить сервис:

```bash
sudo systemctl restart nginx
```

или:

```bash
sudo systemctl start nginx
```

Коротко:

```text
исправить причину мало
нужно заново стартовать сервис
```

---

### Полная диагностическая схема service failed

```text
1. Проверить статус:
   systemctl status service --no-pager

2. Посмотреть последние логи:
   journalctl -u service -n 30 --no-pager

3. Если сервис с конфигом — проверить конфиг:
   nginx -t
   или аналогичную команду проверки для другого сервиса

4. Исправить причину:
   файл
   права
   порт
   синтаксис
   зависимость

5. Перезапустить сервис:
   sudo systemctl restart service

6. Проверить состояние:
   systemctl is-active service
   systemctl status service --no-pager

7. Снова посмотреть последние логи:
   journalctl -u service -n 20 --no-pager
```

## 19. Linux 2.8 — процессы, ресурсы, jobs и kill

### Цель блока

Научиться смотреть реальные процессы в Linux, понимать связь между service и process, находить процессы по имени, смотреть нагрузку CPU/RAM, управлять задачами текущей shell-сессии и корректно завершать процессы.

Этот блок важен для DevOps, потому что почти любая диагностика сервера начинается с вопросов:

- запущен ли нужный процесс;
- какой у него PID;
- кто его запустил;
- сколько он потребляет CPU/RAM;
- есть ли реальные процессы за systemd-сервисом;
- можно ли корректно завершить зависший процесс;
- не зависла ли задача в текущей shell-сессии.

---

### 1. Process, PID, PPID

Процесс — это запущенная программа в Linux.

PID — уникальный идентификатор процесса.

PPID — PID родительского процесса.

Базовые команды:

```bash
ps
ps aux
ps -ef
```

`ps` показывает снимок процессов.

`ps aux` показывает процессы системы в BSD-стиле.

`ps -ef` показывает процессы в System V-стиле и явно показывает PPID.

Пример смысла:

```text
PID  = номер текущего процесса
PPID = номер родительского процесса
```

Например, если процесс был запущен из bash, то bash может быть родительским процессом.

---

### 2. Service vs process

Service — это служба, которой управляет systemd.

Process — это реальный запущенный процесс в системе.

Пример:

```bash
systemctl status nginx
pgrep -a nginx
```

`nginx.service` — это systemd-сервис.

`nginx: master process` и `nginx: worker process` — реальные процессы nginx.

Схема:

```text
nginx.service
    ↓
nginx master process
    ↓
nginx worker process
nginx worker process
```

Важно:

```text
systemctl показывает состояние сервиса.
ps/pgrep/top/htop показывают реальные процессы.
```

Сервис может быть активен, но для диагностики полезно дополнительно проверить реальные процессы.

---

### 3. Поиск процессов

Команды:

```bash
ps aux | grep nginx
pgrep -a nginx
```

`ps aux | grep nginx` показывает все строки процессов, где встречается слово `nginx`.

Разбор:

```text
ps aux      = вывести процессы системы
|           = передать вывод дальше
grep nginx  = оставить только строки со словом nginx
```

Особенность:

```bash
ps aux | grep nginx
```

может показать саму строку `grep nginx`.

Почему?

Потому что `grep nginx` тоже является процессом, и в его командной строке есть слово `nginx`.

Пример лишней строки:

```text
germanix  1234  0.0  0.0  ... grep --color=auto nginx
```

Это не nginx-сервис. Это сама команда поиска.

Более чистый вариант:

```bash
pgrep -a nginx
```

`pgrep -a nginx` ищет процессы по имени `nginx` и показывает:

```text
PID + командная строка процесса
```

Пример:

```text
738 nginx: master process /usr/sbin/nginx -g daemon on; master_process on;
739 nginx: worker process
740 nginx: worker process
```

Преимущество `pgrep -a nginx`:

```text
не показывает лишнюю строку grep nginx;
быстро показывает PID;
показывает командную строку найденного процесса.
```

---

### 4. Nginx master и worker

`nginx master process` — главный процесс nginx.

Он:

- управляет worker-процессами;
- читает конфигурацию;
- контролирует работу nginx;
- создаёт рабочие процессы.

`nginx worker process` — рабочий процесс nginx.

Он:

- обслуживает реальные подключения;
- принимает и обрабатывает запросы;
- работает ниже master-процесса.

Упрощённо:

```text
master = управляющий процесс
worker = рабочий процесс, который обслуживает запросы
```

Для nginx обычно лучше использовать `systemctl`, а не убивать PID руками:

```bash
sudo systemctl restart nginx
sudo systemctl stop nginx
```

Потому что nginx — systemd-сервис с несколькими процессами.

---

### 5. top и htop

Команды:

```bash
top
top -b -n 1 | head -n 20
htop
```

`top` показывает процессы и нагрузку в реальном времени.

`top -b -n 1` делает один неинтерактивный снимок.

`htop` — удобный интерактивный просмотр процессов, CPU, RAM, load average, сортировки и поиска.

Полезные клавиши в `htop`:

```text
F3 — Search
F5 — Tree
F6 — SortBy
F10 или q — Quit
```

Практический смысл:

```text
ps   = разовый снимок
top  = живой мониторинг
htop = удобный интерактивный мониторинг
```

Если сервер тормозит, сначала можно посмотреть:

```bash
top
htop
```

или вывести самые тяжёлые процессы:

```bash
ps aux --sort=-%cpu | head -n 10
ps aux --sort=-%mem | head -n 10
```

Первая команда показывает процессы с наибольшим потреблением CPU.

Вторая команда показывает процессы с наибольшим потреблением RAM.

---

### 6. Jobs

Job — это задача текущей bash-сессии.

Process — это процесс в системе.

Одна job обычно связана с одним или несколькими процессами.

Важно:

```text
process виден через ps/top/htop;
job виден через jobs только в текущей shell-сессии.
```

Текущая shell-сессия в нашей лаборатории — это текущий bash-сеанс внутри Ubuntu, куда мы подключились по SSH.

PowerShell — это окно на Windows.

SSH — подключение к Ubuntu.

Bash — shell внутри Ubuntu.

`jobs` показывает задачи именно текущего bash-сеанса. Если открыть второе SSH-окно, там будет другая bash-сессия и другой список jobs.

---

### 7. Background: запуск задачи в фоне

Команда:

```bash
sleep 300 &
```

`sleep 300` — безопасная учебная команда, которая просто ждёт 300 секунд.

300 — это количество секунд.

Можно было бы написать:

```bash
sleep 60
sleep 255
sleep 500
```

Число не магическое. Это просто длительность ожидания.

Символ `&` означает:

```text
запустить команду в фоне и сразу вернуть управление терминалу.
```

Пример:

```bash
sleep 300 &
jobs
```

Ожидаемый вывод:

```text
[1] 1189
[1]+ Running sleep 300 &
```

Разбор:

```text
[1]  = номер job в текущей shell
1189 = PID процесса в системе
```

---

### 8. Foreground и background

Foreground — передний план.

Команда занимает терминал, и в этой shell-сессии нельзя вводить новые команды, пока foreground-команда не завершится, не будет остановлена или прервана.

Пример foreground-команды:

```bash
sleep 300
```

После запуска терминал как будто “зависает”, но на самом деле bash ждёт завершения команды.

Background — фон.

Команда работает, но терминал свободен для новых команд.

Пример background-команды:

```bash
sleep 300 &
```

После запуска команда работает в фоне, а терминал сразу готов принимать новые команды.

Схема:

```text
foreground = терминал занят задачей
background = задача работает, терминал свободен
```

---

### 9. fg, bg и Ctrl+Z

Команды:

```bash
fg %1
```

`fg %1` возвращает job номер 1 на передний план.

Если выполнить:

```bash
fg %1
```

то задача снова займёт терминал.

`Ctrl+Z` ставит foreground-задачу на паузу, но не убивает её.

После `Ctrl+Z` можно проверить:

```bash
jobs
```

Ожидаемый вывод:

```text
[1]+ Stopped sleep 300
```

Это значит:

```text
job остановлена, но не завершена.
```

Чтобы продолжить остановленную job в фоне:

```bash
bg %1
```

Проверка:

```bash
jobs
```

Ожидаемый вывод:

```text
[1]+ Running sleep 300 &
```

Чтобы вернуть job обратно на передний план:

```bash
fg %1
```

Чтобы завершить job:

```bash
kill %1
```

Проверка:

```bash
jobs
```

Если вывода нет — активных jobs в текущей shell-сессии нет.

---

### 10. kill по job number и PID

Есть два разных варианта:

```bash
kill %1
kill 1225
```

`kill %1` завершает job номер 1 в текущей shell-сессии.

`kill 1225` завершает процесс с PID 1225.

Важно не путать:

```text
%1   = номер job
1225 = PID процесса
```

Практика:

```bash
sleep 500 &
jobs
pgrep -a sleep
kill PID
pgrep -a sleep || echo "no sleep process"
```

Пример:

```bash
sleep 500 &
```

Вывод:

```text
[1] 1225
```

Проверка:

```bash
pgrep -a sleep
```

Вывод:

```text
1225 sleep 500
```

Завершение:

```bash
kill 1225
```

Проверка:

```bash
pgrep -a sleep || echo "no sleep process"
```

Если процесс завершён, вывод будет:

```text
no sleep process
```

Обычный `kill PID` отправляет процессу мягкий сигнал завершения.

`kill -9 PID` — жёсткое завершение процесса.

`kill -9` использовать только если обычный `kill PID` не помог.

---

### 11. Когда использовать kill, а когда systemctl

Для отдельного процесса, учебного `sleep`, зависшего скрипта или ручной задачи можно использовать:

```bash
kill PID
kill %1
```

Для systemd-сервисов сначала лучше использовать:

```bash
sudo systemctl stop nginx
sudo systemctl restart nginx
```

Почему:

```text
systemd знает, как корректно управлять сервисом;
у сервиса может быть несколько процессов;
nginx имеет master/worker процессы;
ручной kill может привести к кривому состоянию;
systemctl корректно обновляет состояние сервиса.
```

Правило:

```text
отдельный процесс — можно kill;
systemd-сервис — сначала systemctl.
```

### 13. Вопросы, которые может задать Денис

#### Что такое процесс?

Процесс — это запущенная программа в Linux.

#### Что такое PID?

PID — уникальный номер процесса.

#### Чем ps отличается от top?

`ps` показывает разовый снимок процессов.

`top` показывает процессы и нагрузку в реальном времени.

#### Что делает ps aux | grep nginx?

Показывает процессы системы и оставляет строки, где встречается слово `nginx`.

#### Почему в ps aux | grep nginx появляется сам grep?

Потому что `grep nginx` тоже является процессом, и в его командной строке есть слово `nginx`.

#### Что делает pgrep -a nginx?

Ищет процессы nginx и показывает PID плюс командную строку.

#### Что такое nginx master process?

Главный процесс nginx, который управляет worker-процессами.

#### Что такое nginx worker process?

Рабочий процесс nginx, который обслуживает реальные запросы.

#### Что такое job?

Job — задача текущей bash-сессии.

#### Чем job отличается от process?

Process — реальный процесс в системе.

Job — задача, которой управляет текущий bash.

#### Что делает sleep 300 &?

Запускает команду `sleep 300` в фоне.

`sleep 300` просто ждёт 300 секунд.

`&` запускает команду в фоне и освобождает терминал.

#### Что делает Ctrl+Z?

Ставит foreground-задачу на паузу, но не убивает её.

#### Что делает bg %1?

Продолжает job номер 1 в фоне.

#### Что делает fg %1?

Возвращает job номер 1 на передний план.

#### Чем kill %1 отличается от kill 1225?

`kill %1` завершает job номер 1.

`kill 1225` завершает процесс с PID 1225.

#### Почему для nginx лучше systemctl restart nginx, а не kill PID?

Потому что nginx — systemd-сервис с master/worker процессами. Systemd корректно управляет сервисом, а ручной kill может привести к неправильному состоянию.

## 20. Linux 2.9 — сеть, IP-адреса, маршруты, порты и проверка nginx

### Цель блока

Научиться выполнять базовую сетевую диагностику Linux-сервера:

- понять, какие IP-адреса есть у машины;
- отличать IP Windows от IP Ubuntu VM;
- проверить наличие маршрута в интернет;
- проверить интернет по IP;
- проверить DNS;
- проверить HTTP/HTTPS через curl;
- увидеть, какие порты слушаются;
- связать сервис, процесс, порт и HTTP-ответ;
- понять ошибку `Connection refused`.

Главная практическая идея блока:

```text
service → process → port → response
```

Для nginx это выглядит так:

```text
nginx.service
    ↓
nginx master/worker processes
    ↓
порт 80 LISTEN
    ↓
curl получает HTTP/1.1 200 OK
```

Если один слой сломан, сервис может быть установлен и даже казаться "почти рабочим", но фактически не отвечать.

---

### 1. IP-адреса и интерфейсы

Команда:

```bash
ip -br a
```

Расшифровка:

```text
ip = утилита для работы с сетью в Linux
-br = brief, краткий вывод
a = address, показать IP-адреса интерфейсов
```

Пример вывода в нашей лаборатории:

```text
lo       UNKNOWN 127.0.0.1/8 ::1/128
enp0s3   UP      10.0.2.15/24 ...
enp0s8   UP      192.168.56.101/24 ...
```

Разбор:

```text
lo = loopback-интерфейс
127.0.0.1 = адрес "самого себя"

enp0s3 = NAT-интерфейс VirtualBox
10.0.2.15 = IP Ubuntu внутри NAT-сети, через него VM выходит в интернет

enp0s8 = Host-only интерфейс VirtualBox
192.168.56.101 = IP Ubuntu для связи Windows ↔ Ubuntu
```

Практический смысл:

```text
Windows PowerShell → SSH → 192.168.56.101 → Ubuntu
```

Когда из Windows выполняется:

```powershell
ssh germanix@192.168.56.101
```

то IP после `@` — это IP удалённой машины, то есть Ubuntu VM, а не Windows.

---

### 2. Почему Windows показывает 192.168.56.1

В Windows PowerShell команда:

```powershell
ipconfig
```

показывает IP-адреса Windows-адаптеров.

В нашей лаборатории:

```text
192.168.56.1 = IP Windows host-only adapter
192.168.56.101 = IP Ubuntu host-only adapter
```

Это две разные машины в одной host-only сети:

```text
Сеть:   192.168.56.0/24
Windows: 192.168.56.1
Ubuntu:  192.168.56.101
```

Важно:

```text
ipconfig показывает IP Windows.
ip -br a показывает IP Ubuntu.
ssh user@IP требует IP удалённой машины.
```

Если забыли IP Ubuntu и SSH не работает:

```text
1. Открыть консоль Ubuntu в VirtualBox.
2. Войти под пользователем germanix.
3. Выполнить:
```

```bash
ip -br a
```

```text
4. Найти IP на enp0s8.
5. Подключиться из PowerShell:
```

```powershell
ssh germanix@192.168.56.101
```

### 3. Маршруты

Команда:

```bash
ip route
```

Смысл:

```text
ip route показывает, куда Linux отправляет сетевой трафик.
```

Главная строка для базовой диагностики:

```text
default via 10.0.2.2 dev enp0s3 proto dhcp src 10.0.2.15 metric 100
```

Разбор:

```text
default = маршрут по умолчанию
via 10.0.2.2 = отправлять через gateway 10.0.2.2
dev enp0s3 = использовать интерфейс enp0s3
src 10.0.2.15 = исходный IP Ubuntu
```

Простыми словами:

```text
Если Linux не знает специальный маршрут до адреса,
он отправляет трафик через default gateway.
```

В нашей VM:

```text
default gateway = 10.0.2.2
интерфейс выхода = enp0s3
```

Это значит:

```text
маршрут в интернет есть через NAT-интерфейс VirtualBox.
```

Ещё есть маршрут host-only сети:

```text
192.168.56.0/24 dev enp0s8 ... src 192.168.56.101
```

Смысл:

```text
сеть 192.168.56.0/24 доступна через enp0s8.
```

Именно поэтому Windows может подключаться к Ubuntu по SSH на:

```text
192.168.56.101
```

### 4. Проверка интернета по IP

Команда:

```bash
ping -c 4 8.8.8.8
```

Расшифровка:

```text
ping = проверить сетевую достижимость
-c 4 = отправить 4 пакета и остановиться
8.8.8.8 = внешний IP-адрес
```

Если результат:

```text
4 packets transmitted, 4 received, 0% packet loss
```

то вывод:

```text
Ubuntu может достучаться до внешнего IP.
Интернет по IP работает.
```

Эта проверка не проверяет DNS, потому что используется готовый IP-адрес.

Если `ping 8.8.8.8` не работает, возможные причины:

```text
нет default route;
сломался NAT;
нет gateway;
проблема VirtualBox adapter;
проблема с интернетом на host-машине;
фаервол/сеть режет ICMP.
```

### 5. Проверка DNS

Команда:

```bash
ping -c 4 google.com
```

Смысл:

```text
проверить достижимость доменного имени.
```

Здесь Linux сначала должен превратить:

```text
google.com
```

в IP-адрес, например:

```text
142.250.120.138
```

Если `ping google.com` работает, то:

```text
интернет работает;
DNS работает.
```

Разница:

```text
ping 8.8.8.8 = проверка связи по IP, без DNS.
ping google.com = проверка связи + проверка DNS.
```

Типовой вывод:

```text
ping 8.8.8.8 работает, ping google.com не работает
```

означает:

```text
интернет по IP есть, вероятная проблема с DNS.
```

### 6. Проверка HTTP/HTTPS через curl

Команда:

```bash
curl -I https://google.com
```

То же самое более читаемо:

```bash
curl --head https://google.com
```

Расшифровка:

```text
curl = сходить по URL и показать ответ
-I = большая I, короткая опция для --head
--head = запросить только HTTP-заголовки
https://google.com = URL
```

Важно не путать:

```text
curl -I URL = curl --head URL
только HTTP-заголовки, без тела страницы.

curl -i URL
заголовки + тело ответа.
```

То есть:

```bash
curl -I http://127.0.0.1
```

или:

```bash
curl --head http://127.0.0.1
```

используется для быстрой проверки:

```text
сервис отвечает или нет;
какой HTTP-статус;
какой Server;
есть ли redirect;
работает ли HTTPS/HTTP.
```

Пример успешного ответа от nginx:

```text
HTTP/1.1 200 OK
Server: nginx/1.24.0 (Ubuntu)
Content-Type: text/html
```

Пример redirect:

```text
HTTP/2 301
location: https://www.google.com/
```

Смысл `301`:

```text
сайт доступен, но перенаправляет на другой URL.
```

### 8. Порты: базовая модель

IP отвечает на вопрос:

```text
к какой машине идти?
```

Порт отвечает на вопрос:

```text
к какой программе внутри этой машины идти?
```

Пример:

```text
192.168.56.101 = IP Ubuntu
22 = порт SSH
80 = порт HTTP/nginx
53 = порт DNS
```

Схема:

```text
клиент → IP сервера → порт → процесс
```

SSH:

```text
Windows PowerShell
    ↓
ssh germanix@192.168.56.101
    ↓
192.168.56.101:22
    ↓
sshd
```

HTTP/nginx:

```text
curl/browser
    ↓
192.168.56.101:80
    ↓
nginx
```

Порт сам по себе ничего не делает.

Работает процесс:

```text
процесс открывает порт;
порт становится LISTEN;
клиент подключается к IP:PORT;
Linux передаёт подключение процессу, который держит порт.
```

Примеры стандартных портов:

```text
21 = FTP
22 = SSH
53 = DNS
80 = HTTP
443 = HTTPS
5432 = PostgreSQL
3306 = MySQL/MariaDB
8080 = часто альтернативный HTTP/dev/proxy port
```

Важно:

```text
номер порта существует всегда;
но порт работает только если процесс его открыл.
```

То есть:

```text
8080 как номер существует,
но если процесс его не слушает,
подключиться не получится.
```

---

### 9. Просмотр слушающих портов через ss

Команда:

```bash
ss -tuln
```

Расшифровка:

```text
ss = socket statistics
-t = TCP
-u = UDP
-l = listening, только слушающие сокеты
-n = numeric, показывать адреса и порты числами
```

Смысл:

```text
показать, какие TCP/UDP-порты сейчас слушает сервер.
```

Команда с процессами:

```bash
sudo ss -tulpn
```

Расшифровка:

```text
sudo = с правами администратора
ss = показать сокеты
-t = TCP
-u = UDP
-l = listening
-p = process, показать процесс
-n = numeric
```

Почему `sudo`:

```text
без sudo Linux может не показать имя процесса/программы.
```

Практический смысл:

```text
без -p видно порт;
с -p видно, какой процесс держит порт.
```

Фильтр по портам 22 и 80:

```bash
sudo ss -tulpn | grep -E ':22|:80'
```

Разбор:

```text
sudo ss -tulpn = показать слушающие порты и процессы
| = передать вывод дальше
grep -E = расширенный шаблон
':22|:80' = строки, где есть :22 или :80
```

`|` внутри grep-шаблона здесь значит "или":

```text
:22 или :80
```

### 10. Как читать вывод ss

Пример:

```text
tcp LISTEN 0 4096 0.0.0.0:22 0.0.0.0:* users:(("sshd",pid=724,...))
tcp LISTEN 0 511  0.0.0.0:80 0.0.0.0:* users:(("nginx",pid=740,...))
```

Разбор:

```text
tcp = TCP-протокол
LISTEN = порт открыт и ждёт входящие подключения
0.0.0.0:22 = порт 22 слушается на всех IPv4-адресах машины
0.0.0.0:80 = порт 80 слушается на всех IPv4-адресах машины
users:(("sshd"...)) = порт держит процесс sshd
users:(("nginx"...)) = порт держит процесс nginx
```

`0.0.0.0:80`:

```text
сервис слушает порт 80 на всех IPv4-адресах машины.
```

У нашей Ubuntu есть несколько адресов:

```text
127.0.0.1
10.0.2.15
192.168.56.101
```

Если nginx слушает:

```text
0.0.0.0:80
```

то он принимает подключения на порт 80 через разные IPv4-адреса этой машины, в том числе:

```text
http://127.0.0.1
http://192.168.56.101
```

`[::]:80`:

```text
IPv6-аналог 0.0.0.0:80.
```

`127.0.0.1:80`:

```text
сервис слушает только loopback-адрес, то есть доступен самой машине.
```


```text
systemctl = сервис запущен?
pgrep = реальные процессы есть?
ss = порт открыт и кем?
curl = сервис реально отвечает?
```

```bash
systemctl status nginx --no-pager
```

```text
systemctl status nginx

показывает реальные процессы nginx.

проверяет HTTP-ответ nginx локально с самой Ubuntu.

curl --head http://192.168.56.101
проверяет HTTP-ответ nginx на host-only IP Ubuntu.
```

Если всё работает:

```text
nginx active
процессы nginx есть
порт 80 LISTEN
curl получает HTTP/1.1 200 OK
```

### 12. Connection refused

`Connection refused` / `Couldn't connect to server` означает:

```text
IP доступен,
но на нужном порту нет процесса, который принимает подключение.
```

Пример с пустым портом 8080:

```bash
curl --head http://127.0.0.1:8080
sudo ss -tulpn | grep :8080 || echo "nothing listens on 8080"
```

Ожидаемый смысл:

```text
curl не может подключиться к 127.0.0.1:8080;
ss не показывает :8080;
значит порт 8080 никто не слушает.
```

Пример с остановленным nginx:

```bash
sudo systemctl stop nginx
systemctl status nginx --no-pager
sudo ss -tulpn | grep :80 || echo "nothing listens on 80"
curl --head http://127.0.0.1
```

Ожидаемый смысл:

```text
nginx inactive;
порт 80 исчез;
curl на 127.0.0.1:80 получает ошибку подключения.
```

Запуск обратно:

```bash
sudo systemctl start nginx
systemctl status nginx --no-pager
sudo ss -tulpn | grep :80
curl --head http://127.0.0.1
```

## 2. Permission denied

### Что значит ошибка

Ошибка:

```text
Permission denied
```

означает:

```text
команда правильная,
объект существует,
но у пользователя нет нужного права на действие.
```

Типовые действия:

```text
читать файл;
писать в файл;
выполнять файл;
входить в каталог;
открывать системный порт;
читать системный лог;
изменять системный конфиг.
```

Типовые DevOps-ситуации:

```text
нельзя записать в конфиг;
скрипт не запускается;
nginx не может прочитать файл;
контейнер не может писать в volume;
GitLab Runner не может открыть файл;
обычный пользователь пытается открыть порт 80.
```

---

### Права Linux

У файла есть три группы прав:

```text
owner  = владелец
group  = группа
others = остальные
```

Базовые права:

```text
r = read = 4
w = write = 2
x = execute = 1
```

Примеры:

```text
400 = r-------- = владелец может только читать
600 = rw------- = владелец может читать и писать
644 = rw-r--r-- = владелец читает/пишет, остальные читают
755 = rwxr-xr-x = владелец всё, остальные читают/выполняют
```

---

### Практический пример

Создать рабочую папку:

```bash
mkdir -p ~/linux-lab/diagnostics
cd ~/linux-lab/diagnostics
pwd
```

Создать файл:

```bash
echo "secret config" > denied-demo.txt
cat denied-demo.txt
ls -l denied-demo.txt
```

Обычные права могут выглядеть так:

```text
-rw-rw-r-- 1 germanix germanix ... denied-demo.txt
```

Смысл:

```text
owner germanix может читать и писать;
group germanix может читать и писать;
others могут читать.
```

Запретить запись даже владельцу:

```bash
chmod 400 denied-demo.txt
ls -l denied-demo.txt
```

Ожидаемо:

```text
-r-------- 1 germanix germanix ... denied-demo.txt
```

Теперь попытаться дописать строку:

```bash
echo "new line" >> denied-demo.txt
```

Ожидаемо:

```text
Permission denied
```

Почему:

```text
>> пытается дописать в файл;
для записи нужно право w;
у владельца права только r;
write-права нет.
```

---

### Диагностика Permission denied

После ошибки не исправлять вслепую. Сначала проверить.

```bash
stat denied-demo.txt
id
```

`stat` показывает подробную информацию о файле:

```text
права;
владельца;
группу;
размер;
inode;
временные метки.
```

Пример важной строки:

```text
Access: (0400/-r--------)  Uid: (1000/germanix)  Gid: (1000/germanix)
```

Смысл:

```text
0400 = права файла;
-r-------- = текстовая форма прав;
Uid germanix = владелец;
Gid germanix = группа.
```

Команда:

```bash
id
```

показывает:

```text
какой у меня UID;
какая основная группа;
в каких группах я состою.
```

---

### Исправление

Вернуть владельцу право записи:

```bash
chmod 600 denied-demo.txt
ls -l denied-demo.txt
```

Ожидаемо:

```text
-rw------- 1 germanix germanix ... denied-demo.txt
```

Теперь запись сработает:

```bash
echo "new line" >> denied-demo.txt
cat denied-demo.txt
```

Ожидаемо:

```text
secret config
new line
```

---

### Диагностическая схема Permission denied

```text
1. Что я пытаюсь сделать?
   читать / писать / выполнить / войти в каталог / открыть порт

2. Кто я?
   id

3. Кто владелец объекта?
   ls -l file
   stat file

4. Какие права у owner/group/others?

5. Есть ли нужное право?
   r для чтения
   w для записи
   x для выполнения/входа в каталог

6. Исправление:
   chmod — изменить права
   chown — изменить владельца
   sudo — выполнить с повышенными правами, если это оправдано
```

Важно:

```text
sudo не надо использовать автоматически.
Сначала понять причину.
```

---

### Ключевой вывод

```text
Permission denied =
нет прав на конкретное действие.

В примере:
файл принадлежал germanix,
но chmod 400 убрал write-право.
Поэтому >> не смог дописать строку.
После chmod 600 запись снова заработала.
```

```text
-rw-rw-r-- 1 germanix germanix ... denied-demo.txt
```

Смысл:

```text
owner germanix может читать и писать;
group germanix может читать и писать;
others могут читать.
```

Запретить запись даже владельцу:

```bash
chmod 400 denied-demo.txt
ls -l denied-demo.txt
```

Ожидаемо:

```text
-r-------- 1 germanix germanix ... denied-demo.txt
```

Теперь попытаться дописать строку:

```bash
echo "new line" >> denied-demo.txt
```

Ожидаемо:

```text
Permission denied
```

Почему:

```text
>> пытается дописать в файл;
для записи нужно право w;
у владельца права только r;
write-права нет.
```

---

### Диагностика Permission denied

После ошибки не исправлять вслепую. Сначала проверить.

```bash
stat denied-demo.txt
id
```

`stat` показывает подробную информацию о файле:

```text
права;
владельца;
группу;
размер;
inode;
временные метки.
```

Пример важной строки:

```text
Access: (0400/-r--------)  Uid: (1000/germanix)  Gid: (1000/germanix)
```

Смысл:

```text
0400 = права файла;
-r-------- = текстовая форма прав;
Uid germanix = владелец;
Gid germanix = группа.
```

Команда:

```bash
id
```

показывает:

```text
какой у меня UID;
какая основная группа;
в каких группах я состою.
```

---

### Исправление

Вернуть владельцу право записи:

```bash
chmod 600 denied-demo.txt
ls -l denied-demo.txt
```

Ожидаемо:

```text
-rw------- 1 germanix germanix ... denied-demo.txt
```

Теперь запись сработает:

```bash
echo "new line" >> denied-demo.txt
cat denied-demo.txt
```

Ожидаемо:

```text
secret config
new line
```

---

### Диагностическая схема Permission denied

```text
1. Что я пытаюсь сделать?
   читать / писать / выполнить / войти в каталог / открыть порт

2. Кто я?
   id

3. Кто владелец объекта?
   ls -l file
   stat file

4. Какие права у owner/group/others?

5. Есть ли нужное право?
   r для чтения
   w для записи
   x для выполнения/входа в каталог

6. Исправление:
   chmod — изменить права
   chown — изменить владельца
   sudo — выполнить с повышенными правами, если это оправдано
```

Важно:

```text
sudo не надо использовать автоматически.
Сначала понять причину.
```

---

### Ключевой вывод

```text
Permission denied =
нет прав на конкретное действие.

В примере:
файл принадлежал germanix,
но chmod 400 убрал write-право.
Поэтому >> не смог дописать строку.
После chmod 600 запись снова заработала.
```

---

## 5. Connection refused

### Что значит Connection refused

Ошибка:

```text
Connection refused
```

или:

```text
Couldn't connect to server
```

означает:

```text
IP доступен,
но на нужном порту нет процесса,
который принимает подключение.
```

Важно:

```text
Это не обязательно проблема сети.
Это часто проблема сервиса/порта.
```

---

### Пример с пустым портом 8080

Команда:

```bash
curl --head http://127.0.0.1:8080
```

Если на 8080 никто не слушает, получим:

```text
Failed to connect to 127.0.0.1 port 8080
Couldn't connect to server
```

Проверка:

```bash
sudo ss -tulpn | grep :8080 || echo "nothing listens on 8080"
```

Ожидаемо:

```text
nothing listens on 8080
```

Вывод:

```text
curl не подключился к 8080,
потому что ss подтверждает:
на 8080 нет слушающего процесса.
```

---

### Пример с остановленным nginx

Остановить nginx:

```bash
sudo systemctl stop nginx
```

Проверить статус:

```bash
systemctl status nginx --no-pager
```

Ожидаемо:

```text
Active: inactive (dead)
```

Проверить порт 80:

```bash
sudo ss -tulpn | grep :80 || echo "nothing listens on 80"
```

Ожидаемо:

```text
nothing listens on 80
```

Проверить curl:

```bash
curl --head http://127.0.0.1
```

Ожидаемо:

```text
Failed to connect to 127.0.0.1 port 80
Couldn't connect to server
```

Смысл:

```text
127.0.0.1 доступен;
но nginx остановлен;
порт 80 пустой;
curl не может подключиться.
```

---

### Запуск nginx обратно

```bash
sudo systemctl start nginx
systemctl status nginx --no-pager
sudo ss -tulpn | grep :80
curl --head http://127.0.0.1
```

Ожидаемо:

```text
nginx active;
порт 80 снова LISTEN;
curl получает HTTP/1.1 200 OK.
```

---

### Диагностическая схема Connection refused

```text
1. Проверить адрес:
   правильный ли IP/hostname?

2. Проверить порт:
   sudo ss -tulpn | grep :PORT

3. Проверить сервис:
   systemctl status SERVICE --no-pager

4. Проверить процессы:
   pgrep -a PROCESS

5. Проверить локально:
   curl --head http://127.0.0.1:PORT

6. Если локально работает, а снаружи нет:
   смотреть bind address, firewall, сеть, маршрут.
```

---

### Ключевой вывод

```text
Connection refused =
машина доступна,
но на указанном порту нет процесса,
который принимает подключение.
```

---

## 6. DNS / network issue

### Главная идея

Когда “интернет не работает”, нельзя сразу говорить:

```text
сломался интернет
```

Нужно проверять по слоям:

```text
1. Есть ли IP?
2. Есть ли маршрут?
3. Есть ли связь по IP?
4. Работает ли DNS?
5. Работает ли HTTP/HTTPS?
```

Диагностическая цепочка:

```bash
ip -br a
ip route
ping -c 4 8.8.8.8
ping -c 4 google.com
curl --head https://google.com
getent hosts google.com
```

---

### 1. ip -br a

Команда:

```bash
ip -br a
```

Проверяет:

```text
есть ли сетевые интерфейсы;
есть ли IP-адреса;
подняты ли интерфейсы.
```

В нашей VM:

```text
enp0s3 = NAT, интернет VM
enp0s8 = Host-only, SSH Windows → Ubuntu
```

Пример:

```text
enp0s3 UP 10.0.2.15/24
enp0s8 UP 192.168.56.101/24
```

Смысл:

```text
у Ubuntu есть IP для NAT-интернета;
у Ubuntu есть IP для SSH с Windows.
```

---

### 2. ip route

Команда:

```bash
ip route
```

Проверяет:

```text
куда Linux отправляет сетевой трафик.
```

Главная строка:

```text
default via 10.0.2.2 dev enp0s3
```

Смысл:

```text
если Linux не знает специальный маршрут,
он отправляет трафик через gateway 10.0.2.2
по интерфейсу enp0s3.
```

Если default route нет:

```text
машина может иметь IP,
но не понимать,
куда отправлять трафик наружу.
```

---

### 3. ping 8.8.8.8

Команда:

```bash
ping -c 4 8.8.8.8
```

Проверяет:

```text
может ли Ubuntu достучаться до внешнего IP.
```

Если:

```text
4 packets transmitted, 4 received, 0% packet loss
```

значит:

```text
связь по IP есть;
маршрут наружу работает;
NAT VirtualBox работает.
```

Эта проверка не проверяет DNS, потому что используется готовый IP.

---

### 4. ping google.com

Команда:

```bash
ping -c 4 google.com
```

Проверяет:

```text
может ли Ubuntu превратить google.com в IP
и получить ответ.
```

Если:

```text
ping 8.8.8.8 работает,
ping google.com не работает
```

вероятный вывод:

```text
интернет по IP есть;
проблема с DNS.
```

---

### 5. curl --head https://google.com

Команда:

```bash
curl --head https://google.com
```

Проверяет:

```text
работает ли HTTP/HTTPS-доступ.
```

Пример ответа:

```text
HTTP/2 301
location: https://www.google.com/
```

Смысл:

```text
сайт доступен;
HTTPS работает;
301 = redirect, не ошибка.
```

---

### 6. getent hosts google.com

Команда:

```bash
getent hosts google.com
```

Проверяет:

```text
во что система резолвит доменное имя.
```

Пример:

```text
142.250.120.138 google.com
```

или IPv6-адреса:

```text
2a00:1450:4025:807::64 google.com
```

Смысл:

```text
системный DNS-резолвинг работает.
```

---

### Диагностическая схема DNS / network

```text
ip -br a
есть ли IP?

ip route
есть ли default route?

ping -c 4 8.8.8.8
есть ли связь по IP без DNS?

ping -c 4 google.com
работает ли DNS + связь?

curl --head https://google.com
работает ли HTTP/HTTPS?

getent hosts google.com
во что система резолвит домен?
```

---

### Типовые выводы

```text
ping 8.8.8.8 не работает
→ проблема может быть в маршруте, NAT, gateway, сети хоста, firewall.

ping 8.8.8.8 работает,
ping google.com не работает
→ вероятно DNS.

ping работает,
curl не работает
→ проблема может быть на HTTP/HTTPS, proxy, firewall, TLS, сайте.

default route нет
→ машине некуда отправлять трафик наружу.

getent hosts google.com возвращает адреса
→ DNS-резолвинг работает.
```

```text

command not found

command -v COMMAND

опечатка;
```

```text
Permission denied

нет read/write/execute;
```

```text

service failed

Проверки:

Для nginx:
sudo nginx -t

сломанный конфиг;
порт занят;
нет прав;
нет файла;
ошибка запуска.
```

## 8. Главный вывод блока

```text
Диагностика = не угадывание.

Нужно идти по слоям:

1. Что сломалось?
2. Какой симптом?
3. Какая команда проверяет этот слой?
4. Что показывает вывод?
5. Какая вероятная причина?
6. Как исправить?
7. Как проверить, что исправление сработало?
```

Для сервисов:

```text
systemctl → journalctl → service-specific check → fix → restart → status
```

Для nginx:

```text
nginx -t → systemctl restart nginx → status → journalctl
```

Для портов:

```text
ss → process → port → curl
```

Для сети:

```text
ip → route → ping IP → ping domain → curl → getent
```

Для прав:

```text
id → ls -l/stat → chmod/chown/sudo
```

Для команд:

```text
command -v → dpkg/apt → PATH
```

Ключевая рабочая фраза:

```text
Я не просто ввожу команды.
Я проверяю слой системы и доказываю причину.
```
